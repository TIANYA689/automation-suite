## 核心判据

**HAR 里最值钱的不是"请求长什么样"，而是"哪些参数每次请求都在变"。**

前者照抄即可，它决定脚本能不能跑起来；后者决定脚本能不能跑第二次。
一份 HAR 里通常只有两三个参数是真正难的（签名、加密字段、时间戳配对），
其余几十个都是常量。把注意力按这个比例分配，是整条流水线里唯一重要的事。

由此推出第二个判据：**形态不等于算法**。HAR 能告诉你某个参数是"32 位十六进制、
每次请求都不同"，但告诉不了你它是 `md5(uid + ts + key)` 还是服务端下发的随机串。
凡是把形态当算法、用一个假值顶上，脚本会看起来跑通了、实际每次都被服务端拒绝——
**静默猜错的默认值，比一条明确的待办昂贵得多**。

## 四段流水线

| 段 | 谁做 | 产出 | 项目内工具 |
|---|---|---|---|
| 1 盘点 | 自动 | 接口地图：域名、接口清单、凭证字段、签名候选、易变参数候选、调用时序 | `scripts/automation/har_probe.py` |
| 1′ 溯源 | 自动 | 某个值来自哪条响应：来源 / 回显 / 回声 / 同长候选 | `scripts/automation/har_origin.py` |
| 1″ 源码 | 自动 | 内嵌前端源码里的线索：字段生成规则、请求包装族的编码方式、鉴权拦截器、业务码、完整接口面 | `scripts/automation/har_source.py` |
| 2 意图声明 | **人 / 代理** | 哪个接口是登录、哪个是任务、哪些参数要生成、路径 `{id}` 从哪来 | `<name>.plan.json` |
| 3 校验 | 自动 | 声明与抓包证据是否自洽 | `har_to_script.py --check` |
| 4 生成 | 自动 | 符合套件范式的脚本骨架 + 待人工完成清单 | `har_to_script.py --out` |
| 4′ 回填 | **人 / 逆向** | 复现产物写进 `dynamic`，由生成器内联进骨架 | `<name>.plan.json` 的 `dynamic` |
| 5 固化 | 自动 | 脱敏且保形的合成夹具，供回归 | `scripts/automation/har_to_fixture.py` |
| 6 验证 | 自动 | 把骨架装进桩会话跑判定逻辑，**不发真实请求** | `scripts/automation/stub_session.py` |

第二段是整条链的关键：**把"语义判断"从一次不可复查的脑内推理，变成一份可 diff、
可评审、可回归的落盘产物**。工具不猜哪个接口是签到，但会强制这个问题必须被回答——
`role` 没填就拒绝生成。

## 夹具的两条硬要求

真实抓包含凭证，不能进仓库；但夹具也不能是"删干净就完事"。降级（第 5 段）有两条硬要求：

**一、替换必须保形。** 把 `sign` 的值换成 `REDACTED` 之后，`har_probe` 再也判不出它是
hex32，`har_to_script` 也就推不出策略——夹具变成废纸。所以替换按值的形态走：
hex32 换 hex32、UUID 换 UUID、纯数字换等长数字串（并保留首位，否则一个"10 位但不在
时间戳区间"的数字可能被替换进区间，形态判据从 `number` 变成 `timestamp_s`——替换动作
自己制造了假证据）。

**二、替换必须确定。** 同一个原值永远映射到同一个假值（由哈希派生，不用随机数）。
整条链的核心判据是"哪些参数每次都在变"，如果替换动作自己引入随机性，常量会看起来像
变量、变量之间的相等关系也会断掉——**夹具会把要测的东西测坏**。确定性还附带一个好处：
同一份抓包每次降级得到逐字节相同的结果，夹具可以 diff。

验收标准只有一条：**降级之后，判据还成立吗**。`har_to_fixture.py` 把它做成内置的两道关——
泄漏自检（原 HAR 的任何值都不出现在夹具里）与证据保真度（端点集合与参数形态前后一致）。
任一不过就拒绝写出文件。时间戳是唯一的例外，它保留原值：不是凭证，而且是"参数在变"
最直接的证据。

## 两个静默出错点

这条流水线真正会翻车的地方不在"生成不出代码"，而在**生成出能跑但结论是错的代码**。
实测踩到两个，都属于同一类：脚本报绿，实际什么都没做。

**一、HTTP 200 不等于业务成功。** 国产 App 的接口普遍把成败放在响应体的业务码里，
HTTP 状态一律 200。实测样本：签到接口返回 `{"code":500,"msg":"今日已经签到，请明日再来"}`，
HTTP 状态 200；同一次抓包里另外 8 个接口返回 `{"code":0,"msg":"操作成功"}`。
只看 `status_code` 的骨架会把"今天已经签过了"报成成功——**脚本每次运行都报绿，
而它从来没有真的签成过**。所以声明里要有 `expect`（`code_field` / `success_values`，
可再加 `benign`），生成的代码按业务码判定，不按 HTTP 状态判定。

`benign` 必须用 `msg_contains` 收窄，不能只写 `value`。否则服务端真的返回 500
（内部错误）时也会被当成"今天签过了"咽下去——**把错误码当成功码用，是比不判定更坏的情况**。

还有一层诚实性要求：`success_values` 永远只是**声明**。如果抓包里根本没有一次成功样本
（很常见——抓包那天用户已经签过了），这个值就是从兄弟接口推断的。工具验不了这件事，
只能在待办清单里点名让人去验，不能让它悄悄变成一个既定事实。

**二、占位符必须有来源。** 骨架里 `headers: {"Authorization": "Bearer {token}"}`
这种模板，运行时的取值来源只有三个：账号字段、动态参数、前序步骤的 capture。
三个都没有时，生成的代码会走 `state.get(name, "")` 拿到空串，拼出 `"Bearer "` 发出去，
服务端回 401——**脚本没崩，只是永远不成功**。

这个缺口在"长期令牌 + 无登录流程"的抓包里最容易踩：令牌 35 次请求都是同一个值、
登录接口根本不在抓包里，于是没有 capture 可以依赖。修法是两处一起：
账号字段在客户端初始化时先落进 state（静态凭证打底），登录步骤的 capture 覆盖同名键
（动态令牌覆盖）；校验器则要求每个模板槽位都能在这三者之一里找到来源，
找不到就报 `unresolved_slot` 并列出当前可用集合。

推论：**同一个步骤不能使用它自己 capture 的槽位**。capture 发生在响应之后，
同一个请求用不上——这是鸡生蛋，必须拦。

## 协议层产物与跨域名端点

抓包里的端点数不等于业务端点数。实测一份 21 个端点的抓包，其中 10 个不承载任何业务意图：

- **CONNECT** 是代理隧道，永远不是接口。
- **OPTIONS** 与**同路径**的其它方法并存时是 CORS 预检（浏览器自动发出，业务代码从不主动调）。
  只有同路径没有别的方法的 OPTIONS 才保留——那可能是能力探测，需要人来判。

这两个判据是**结构性的**（判据是 HTTP 协议本身），不是语义判断，所以工具可以自动承担，
不违反"工具不猜语义"。但要注意两点：

一是**剔除必须被说明**。工具不能静默删掉端点，否则人永远不知道分类器吃掉了什么。
计划模板的说明里要列出被剔除的端点与理由，脚本待办里也要有一行汇总。

二是**剔除必须可回退**。默认不进步骤，但校验器的白名单仍然包含它们——
人若判断某个 OPTIONS 确实是业务接口，加回去必须被放行。

另有一类不能剔除、只能点名的：**跨域名端点**。它们几乎总是第三方（验证码 / CDN / 统计），
但也可能真的要走（比如拿验证码令牌）。所以工具只汇总一行"这些端点不在主接口域名上"，
由人决定留或删——**剔除是替人做决定，点名是把决定交还给人**。

## 零参数的请求体

`Content-Length: 0` 不代表"没有请求体约定"。实测签到接口是
`POST` + `Content-Type: application/x-www-form-urlencoded` + `Content-Length: 0`，
即"空表单"。骨架若因为 payload 为空就干脆不传 `data`，会连 `Content-Type` 一起丢掉，
服务端可能直接拒。正确做法是传一个空 dict——`requests` 传 `data={}` 正好复现
"空表单"这个形态，而"不传"复现不出来。

## 外部输入与第三方令牌

抓包里有一类字段，值在抓包里存在、但脚本永远自己产不出来。它们不改变代码的写法，
它们改变代码的**结构**。

**一、发送验证码类接口要先问"码从哪来"。** 实测 `getAuthCode` 只返回
`{"code":0,"msg":"验证码发送成功"}`，6 位验证码发到邮箱——抓包里根本没有这个值。
若把它当成一个能自动完成的步骤，脚本会永远卡在下一步。凡这类接口都要在计划里声明为
**人工介入点**，并把下游步骤的验证码字段标成 `env:` 来源。验证码的有效期、每天可发几次，
抓包都看不出来，要写进待办让人确认。

**二、判定"某字段是第三方令牌"要靠哈希相等，不能靠名字。** 字段名叫 `token` 的满地都是，
名字不构成判据。做法：把第三方域名（验证码 / CDN / 统计）侧所有响应体里长度 ≥200 的串
做 sha256 建索引，再看业务请求里该字段的值是否命中。实测 5/5 命中，长度 804 / 825 / 846，
前缀 `03AFcWeA` 与 `0cAFcWeA`。**"它等于第三方响应里的某个串"才是判据，名字不是。**

由此得到三个结论，每一个都改变脚本形态：

- 令牌是**一次性的**（约 2 分钟 TTL），每跳都要重新取——所以链只能拆成多个脚本，
  一次运行跑不完；
- 三个接口之间的令牌**不通用**，不能拿一个顶三个；
- 令牌只能由**操作者在浏览器里取出**，经 `env:` 注入。复现它的生成过程属于
  "让校验不生效"，不在本流水线范围内（见 `docs/upstream-absorption.md` 的切片判据）。

## 人工环节的交接

上一节说的是「哪些值脚本产不出来」。这一节说的是**怎么把这件事交给执行环节**——
两者的区别是：前者是识别，后者决定这一步会不会被跳过。

**只写在说明里的提醒等于没有。** 令牌原先只是计划里一个 `env:` 名字，加上说明里
一句「每次运行都要重新取」。跳过它的表现不是一句「你忘了取令牌」，而是**脚本报一个
看不懂的服务端错误**（令牌为空 → 服务端拒绝）——又是那类静默失败。凡是执行环节
需要照做的事，要么是数据，要么是判据，不能是散文。

**做法：把人工环节声明成数据。** 每一步写清三件事——填哪个槽位、属于什么类型的挑战、
**值能不能跨运行复用**。第三件是重点，因为一次性挑战的真正代价在这里：一个需要三次
调用的工作流需要三份**新鲜**的值，而 `fresh_per_run` 一旦成为一等字段，它就能被校验、
被打印、被排进运行顺序，而不必等到运行时才发现。

**覆盖性自检必须双向。** 只查一个方向会漏：

- 计划里出现、而声明里没有的 `env:` 槽位 → 拒（「计划新加了环境变量」不会被静默漏掉）；
- 声明说某个计划要用它、而那个计划的 `env:` 里没有 → 拒（「归属写错了」不会被静默漏掉）。

**值只交付一次，且不进审计。** 收集函数返回一次即不再持有；摘要只报长度；
唯一带值的地方是给操作者看的终端输出——**终端是交付通道，审计文件不是**。
审计只记 origin、挑战类型、状态与时间。

**为什么不外包给打码服务。** 这是最容易被提出来的一条路，值得把理由写死：

1. 那是**让校验不生效**，不是搞清楚状态。按「这一步是在搞清楚状态，还是在改变状态」
   切片，它属于剔除项；接上它还会让交付物里「授权边界」一节的声明变成假话。
2. 技术上也常常对不上：常见打码模块实现的是 reCAPTCHA **v2** invisible 流程，
   而 v3 需要 `version=v3` 与 `action`，参数不匹配。
3. v3 的分数是按**产生令牌的那个浏览器会话与 IP** 评估的。农场产出的令牌通常低于
   站点阈值，失败时表现为 HTTP 200 + 业务错误码——正是最坏那类静默失败。

替代做法不复杂：令牌仍由操作者在自己的浏览器会话里完成，工具只负责**接收、绑定、
交付**。这样「取一个令牌」这件事同样被解决了，只是回答挑战的人仍然是本人。

## 条目顺序不携带时间信息

**HAR 规范不要求 `entries` 按时间排。** 实测 ProxyPin 1.2.4 导出的四份真实抓包，
`entries` 数组基本是**倒序**（最新在前），而且不是严格倒序——相邻两项时间递增的比例
分别是 5/148、0/10、3/122、1/36，最大位置偏差等于条目数减一。也就是说
**数组下标与时间先后无关，甚至方向相反**。

这个坑不会报错，它只会给出一份看起来很像、方向恰好相反的时序图：签到显示成发生在
登录之前。凡是"谁先谁后"的推理——调用链、字段溯源、步骤顺序——都必须先按
`startedDateTime` 排序。

两个配套要求：

- **修正要看得见。** 盘点输出里要有 `summary.entry_order`（`chronological` /
  `reversed` / `unsorted`）与一行提示，渲染的调用时序标题也要写明"已重排"。
  静默修正与不修正一样危险：读者会以为那就是文件里的原样。
- **缺时间戳的排最后，同刻的按原下标稳定。** 否则同一刻的条目在两次运行里可能换位，
  判定就不可复现。

## 字段溯源：这个值是从哪条响应来的

「判定某字段是第三方令牌要靠哈希相等」（见「外部输入与第三方令牌」）是这条判据的
第一次使用。把它做成工具时要回答的不止"有没有命中"，还有**命中的方向**。

`scripts/automation/har_origin.py` 的做法：把每条**响应**里的候选值做 sha256 建索引，
再拿目标请求的字段值去查这个索引。命中是观测事实——同一个串在两处出现过。
输出只给长度与 12 位哈希前缀，**从不打印明文**：这个值往往上千字符，打印它既读不出
结论，又把凭证写进了终端与日志。

判定有六种，其中两种**不是证据**：

| 判定 | 含义 | 是证据吗 |
|---|---|---|
| `origin` | 命中**更早**的响应，且域名符合 `--from` | 是 |
| `other` | 命中更早的响应，但域名不在 `--from` 里 | 是，但来源不是你以为的那个域名 |
| `echo` | 只命中**同一条 entry 自己的响应** | 是（说明发出去的值被原样回显） |
| `later` | 只命中**更晚**的响应 | **不是**：值先被发出去，之后才出现在响应里 |
| `shape` | 没命中，但池里有同长度、同形态的串 | **不是**：只是线索，来源未证实 |
| `miss` | 都没有 | — |

四个把这件事做对的关键：

**一、池子要收两类来源。** 只收响应体不够——实测这个 API 的令牌走 `Authorization`
**请求头**，而 `Set-Cookie` 这类凭证只出现在**响应头**里，从不出现在响应体里。
所以池子同时索引响应体的长串与响应头的值；头值还要按 `;` 切段、取第一个 `=` 之后的
部分，因为 `名字=值; Path=/; HttpOnly` 这种复合结构里，目标侧拿到的只是其中的**值**，
整条头值不可能与它相等。

**二、域名过滤只能区分 `origin` 与 `other`。** 把 `--from` 套到 `echo` / `later` 上，
会让这两类被误标成 `other`——那是把"值从哪来"和"来源是不是你要的域名"两件正交的事
混成一件。`echo` / `later` 是纯粹的时序事实，与域名无关。

**三、`shape` 要同时比长度和形态。** 只比长度会天天误报：池里的串都是连续
base64url 形态（正则只认这种），而 `User-Agent` 也有 200 来字符、带空格和分号，
长度一撞就成了"同长候选"。加上形态判据，噪音立刻归零。

**四、池子残缺时必须说出来。** 响应体是 base64 的读不出内容，池子就是残的。此时
"没命中"只等于"在这份残池里没找到"，不等于"没有来源"——输出里要有
`pool.complete: false` 与一行显式提示。

**五、字符集必须容得下点号，否则 JWT 根本进不了池子。** 第一版把池子的字符集定成
`[0-9A-Za-z_-]`，于是 `头.载荷.签名` 在每个点号处被切断：整个 JWT 从来不在池里，
而它的三个**段**反而都在。工具于是对它最该回答的那类值报 `miss`——不是没有来源，
是看不见。实测这个 App 的 `Authorization` 正是 20 / 82 / 86 三段的 JWT，池子修好
之后同一条抓包的命中数从 3 涨到 37。

不能顺手把 `=` 也塞进字符集：那会让 `sign=abcdef` 被当成一个整体串，拿裸值
`abcdef` 去查又 miss 了。**补位要在目标侧剥，不能靠扩大字符集**。

这个字符集是**一个共享常量**（`POOL_CHARS`）：池子的长串正则与 `BLOB_RE` 都从它派生。
两处各写一份字面量，改一处漏一处就会把同一个 bug 种回去——而且第二次不会以
"JWT 被切断"的形式暴露，而是以"两套正则对同一个串给出不同判断"的形式，更难看出来。

**六、目标侧的值常被包了一层，要按几种形态各试一次。** `Authorization: Bearer <jwt>`、
base64 尾部的 `=`、`sid=<值>`——整串直接查必然 miss。所以查表前按"原样 / 去前缀 /
去补位 / 等号后段"各试一次，**并且把命中的是哪一种写进结果**（`matched_form`）。
这几条都是机械分解，不是猜语义；写出来是为了让人能自己复核，而不是信一个黑箱结论。

顺带一个副产品：登录响应是 `{"code":0,"msg":"...","data":"Bearer <jwt>"}`，
**`data` 就是完整的头值（含 `Bearer ` 前缀）**。所以计划里 `capture: {authorization: data}`
配 `Authorization: {authorization}` 是对的——要是再自己拼一个 `Bearer `，就会变成
`Bearer Bearer <jwt>`。这类"值里已经带了协议前缀"的坑，只有把响应结构（值只给长度
与哈希）摆出来才看得见。

**输入必须是真实抓包。** 降级夹具刻意丢掉了响应体（它的职责是保住"参数形态"那一层
判据），拿夹具跑溯源只会得到一份全空报告——那不是"没有来源"，是"没有材料"。
所以这个工具与真实抓包同属本地，不进仓库、不进 CI。

顺带暴露出一条夹具侧的真问题：降级器原先把时间戳硬编码成 `.000Z`，等于把所有条目
压到整秒。实测 reCAPTCHA 令牌与用它的请求之间只差 0.24~0.39 秒，全都会被压成同一刻
——「来源」于是静默退化成「回显」。降级只该改**值**，不该改**精度**。

## 内嵌源码：最容易被漏掉的一类证据

盘点器把 `.js` / `.css` / 图片一律归为"静态资源"并折叠掉。那对它的本职（列接口清单）
是对的——静态资源不是接口。但这个默认会让**证据最强的一类**整体消失：前端应用把自己的
代码发给了浏览器，抓包把它原样存了下来。

实测代价。本项目的作业计划里写过这样一句：

> deviceUuid 是 13 位标识符，抓包里只有一次样本、形态是 plain，**看不出生成规则**，
> 也看不出是否与账号绑定。

而生成规则就躺在同一份抓包内嵌的登录页脚本里：

```js
// 抓包内嵌源码 js/8176.b4c9c7c2.js（6.8 KB 的登录页 chunk）的正文
let l = localStorage.getItem("deviceUuid");
l || (l = Math.random().toString(36), localStorage.setItem("deviceUuid", l))
```

所以 `deviceUuid` 是**客户端随机数**，缓存在 `localStorage`，不掺任何账号输入——
"是否与账号绑定"的答案是明确的**否**，不是"看不出"。这不是"看了没找到"，
是**没有去这一类材料里看**。它的产物是一句写进计划的、看起来很像结论的错误陈述，
正好是这条流水线最想防的那种失效：**工具跑得动、报告看起来完整、结论是空的。**

同一份文件里还能量出下面这些，全部是**源码级**证据，不是从几个样本反推的猜测：

| 能拿到什么 | 实测结果 |
|---|---|
| 请求包装族与各自的编码方式 | 四个函数：`GET` / `urlencoded`（`qs.stringify`）/ `JSON` / `multipart` |
| 鉴权头从哪来 | 请求拦截器：`Authorization` 直接取 `localStorage["token"]`，**不拼前缀**，且无条件先置空 |
| 业务失败码的含义 | `code === 5000` → 清掉本地 token 并跳登录页，即"凭证失效" |
| 基址与超时 | 基址常量 + 30 秒超时，路径由 `${基址}/app/...` 拼出 |
| 完整接口面 | **73 个接口**（含路径参数名），而抓包实际只走过其中一小部分 |

四个包装族的意义在于：它把"这个接口的 body 该怎么编"从一个**观测**升级成一个**规则**。
原先只能看抓包里那几次请求长什么样；现在可以对着源码问"这个包装族用在哪"，
于是**没被走到过的接口也知道该怎么编**。而且它给出一致性检查：实测的五个业务请求
（取验证码 / 注册 / 登录 / 实名认证 / 签到）与源码的包装族**逐个吻合**——
计划里的 `body` 字段因此从"照着抓包抄的"变成"被源码确认过的"。

做法（都很机械，不需要理解业务）：

1. **先找接口定义模块。** 它通常是应用自己的、最大的那个 `.js`。
   特征很明显：一大片形如 `` (0,n.hd)(`${n.pc}/app/...`,t) `` 的短函数。
2. **再找包装族的定义。** 在同一个文件里搜导出映射（`{hd:()=>X, Jt:()=>Y, ...}`），
   拿到每个短名背后的真实函数体——编码方式就写在 `Content-Type` 里。
3. **再找拦截器。** 搜 `interceptors.request` / `interceptors.response`：
   鉴权头怎么塞、业务码怎么判、失败怎么处理，都在这一段。
4. **最后才是拿字段名去搜。** 这一步最省事，也最容易忘——所以工具把它做成第一个入口。

三条纪律：

**一、"没命中"与"没材料"必须分开说。** 资源若是 base64 编码就读不出内容，
此时 0 命中只等于"在这份残材料里没找到"。降级夹具更是如此：它把响应体压成了形态占位，
**源码根本不在里面**，跑出来必然是一份空报告。这与「字段溯源」的 `pool.complete` 是
同一条纪律——把"残缺"说成"没有"，正是当初那个错误结论的成因。

**二、命中不是结论。** 源码里出现一个字段名，只说明"这个名字在这份资源里出现过"。
它是不是那个字段的生成规则、这段代码有没有真的跑到，仍然要人判断。工具不猜语义。

**三、掩码是降噪与防误贴，不是安全边界。** 默认把上下文里又长又不透明的串
（长度 ≥ `--mask-min`，缺省 40；字符集是 base64url 那一类；且同时含大小写与数字）
换成长度加指纹，
于是 JWT 与大块 base64 被掩掉，而 URL、MIME 类型、代码标识符原样留着。
真正的边界是**别拿凭证当 needle 去搜**——工具只保证"你搜什么就照着找"，
不保证"你搜的东西适合出现在终端里"。

**输入必须是真实抓包。** 与「字段溯源」同理：夹具里没有源码。本工具与真实抓包同属本地，
不进仓库、不进 CI。

## 复现产物的回填

上一节解决的是「值取不到」。这一节解决另一半：**算法推不出来**。

签名这类参数，生成器只能留一个抛错的桩，清单上多一条「复现参数 X 的生成算法」。
这条待办原先**永远不会消失**——因为工具没有接收产物的入口，人复现完了也只能手改骨架，
而手改的骨架下次重新生成就被覆盖掉了。**一条不可能被消掉的待办，等于一条装饰。**

入口做成一件事：让 `dynamic` 的值除了字符串，还可以是一个对象。

```json
"sign": {
  "impl": "python",
  "source": "impl/sign.py",
  "entry": "compute_sign",
  "verified": {
    "against": "capture/x.har#POST /v1/sign/in",
    "input": {"uid": "12345", "ts": 1758700000, "nonce": "n-1"},
    "expect": "a1b2c3d4e5f6a7b8c9d0e1f2a3b4c5d6"
  }
}
```

生成器把产物原文内联进 `Dynamic` 的对应方法，并生成 `--selftest`。

**核心判据：回填不等于消待办，带证据的回填才消。** 这是整节最重要的一条。
把回填直接等同于完成，待办清单会在第一次回填后变成一张空头支票——而清单一旦失信，
后面所有「明确的待办」都不再有人认真看。所以状态是**三态**，不是两态：

| 计划里长什么样 | 待办 | 生成物 |
|---|---|---|
| `"sign": "UNRESOLVED"` | 「复现参数 sign 的生成算法」 | 抛 `NotImplementedError` 的桩 |
| 对象，无 `verified` | 「已回填，但没有任何验证证据」（**换了说法，不是消失**） | 内联的实现 + 自检时点名 |
| 对象，有 `verified` | 无 | 内联的实现 + 自检可复核 |

`verified` 里 `against` 与 `expect` 都是必填：`against` 记证据来自哪个抓包与端点，
`expect` 是期望值。少了任何一个，这条「验证」就无从复核，**等于没有证据**。

**四条实现约束**，每一条都是被具体故障逼出来的：

**一、产物必须是仓库里一个真实文件，不能是计划里的一段内联字符串。**
内联字符串无法被 review、无法被独立测试、diff 出来是一坨转义。生成器按**计划文件所在目录**
解析 `source`，文件不在就直接拒——「换台机器生成不出来」要在校验期暴露，不是在运行期。

**二、内联是有损变换，所以只放行声明类顶层语句。** 产物顶层的语句会落进方法体，
届时变成「每次调用都执行」。产物文件很自然地带一个 `if __name__ == "__main__"` 自测块，
内联后就成了每次算签名都跑一遍的东西。所以顶层只允许 import / def / class / 赋值 / docstring，
其余一律拒并指出行号。同理，`async` 入口也拒——本流水线只支持 oop 范式，不生成事件循环。

**三、产物收整个 payload，返回字符串。** 签名通常要吃 body 里好几个字段，
而字典字面量**内部引用不了自己**。所以约定产物接收整个 payload，生成器在字典构建完之后
单独赋值一行 `payload["sign"] = Dynamic.sign(payload)`。约定写死是为了让生成器**不用猜参数顺序**——
猜错就是静默错值。

**四、自检不拖网络栈。** 自检只算签名，用不到 `requests`。让 `requests` 的缺失挡住自检，
等于把「复核产物」这件最该随时能做的事，绑在一堆无关依赖上。生成的骨架因此把
`import requests` 放进 `if "--selftest" not in sys.argv:` 分支。

**JS 产物要显式授权。** 复现出来的产物常常是一段 JS，跑它需要 node——那是**外部运行时**。
计划里必须写 `allow_external_runtime: true`，否则拒生成：让生成的脚本去调外部进程是能力越界，
必须由计划显式授权，不能由工具替人决定。JS 源码以原始字符串常量**内联**（生成的骨架必须自包含，
不能依赖旁边那个 `.js` 文件），所以源码里含三引号就直接拒。本机没有 node 时，
`_run_node` 明确报错——**绝不退回一个假值**。

**自检的价值在于能证伪。** 一个永远说「通过」的自检等于没有自检。验收方式很直接：
把 `expect` 改错一位，`--selftest` 必须报 `[不一致]` 并以非零码退出。
另外，自检输出走和正文同样的脱敏（`_mask`），所以期望值不会以明文落在终端里；
这也意味着**夹具里的值不能太短**——`_mask` 对 ≤8 字符的值整段遮掉，报「不一致」时
就看不出差在哪。真实签名没有这么短的。

## 桩会话：判定逻辑怎么在没有网络的情况下被验

生成器只能保证「请求拼得对」。**判定逻辑对不对是另一件事**，而它恰恰是最容易错、
也最贵的一件——业务码型接口下，判定错了的表现是「脚本每次运行都报绿，
而它从来没有真的成功过」。

所以流水线要有第 6 段：把生成的骨架装进一个**假 requests**，喂真实形态的响应，
看它判得对不对。

**做法**：`requests` 被换成一个按顺序吐出预设响应的桩；骨架的 `main()` 照常跑，
只是所有请求都落在桩上。于是整件事可以在 CI 里跑、在没有账号的机器上跑、
在没有网络的机器上跑。

**它不是重放器。** 桩响应完全由调用方给出，这个模块**不读抓包、不知道任何真实接口的形态**。
往桩里喂什么，是用例作者的事——这条边界让它保持成一个测试工具，
而不是一个「自动打真实接口」的东西。

三个实现上的要点，每个都对应一种会让人误判的失败：

**一、`ok` 不能看退出码。** 生成的 `main()` 只在「没配账号」和「NotImplementedError」
时返回非零；**某一步失败它仍然返回 0**（`run()` 里的 `return False` 不外传）。
所以「脚本没崩就算过」在这里是错的，桩会话要翻译的是**输出里的 `[失败]` 标记**。
这是骨架的既有约定，工具不改它，只把它翻成一个好用的布尔。

**二、每次请求的实参都要记下来。** 「multipart 走的是 `files=` 还是 `data=`」
「登录捕获的令牌有没有进到下一步的 header」——这类断言没有请求记录就写不出来，
只能靠肉眼看输出。记录里存的是**真正发给 requests 的那一层**，所以键名是 `json=`、
`data=`、`files=`，而不是骨架自己的形参名。

**三、副作用必须清干净。** 桩会话要临时改 `sys.modules["requests"]`、`sys.argv`、
`sys.stdout` 和环境变量——跑完一个都不能留。测试工具污染测试环境是最难查的一类问题：
它不会当场失败，只会让**后面**某个不相干的用例诡异地挂掉。

**自检路径要能被证明。** `--selftest` 只算签名、用不到网络栈，这一点不该是「碰巧环境里
有 requests」。所以桩会话提供 `run_selftest()`：它会**刻意把 requests 从 `sys.modules`
里摘掉**再跑，让那条设计被证明而不是被假设。

**能力进仓库，用例随作业走。** 装载与记录是通用能力，属于套件；「阿瓦隆的注册接口
返回 `{"code":500,"msg":"验证码错误"}`」是作业数据，属于作业。混在一起，
要么套件里塞满别人的接口细节，要么作业丢了下一次得重写。

## 判据：什么必须由人决定，什么可以自动

| 环节 | 归属 | 理由 |
|---|---|---|
| 接口归并（数字/UUID/哈希归一成 `{id}`） | 自动 | 纯字符串处理 |
| 静态资源剔除 | 自动 | 后缀与 MIME 可判 |
| 参数形态分类（哈希 / 时间戳 / 随机数） | 自动 | 值本身的形态可判 |
| 协议层产物剔除（CONNECT / 同路径预检 OPTIONS） | 自动 | 判据是 HTTP 协议本身，不是语义 |
| 跨域名端点**点名** | 自动 | 判据是 host 与主接口域名是否一致 |
| **跨域名端点留不留** | **人** | 可能是第三方，也可能是要走的一步 |
| 业务码判定的**结构**（哪些字段、怎么比） | 自动 | 声明给出后按声明生成 |
| **业务码的取值**（成功码是多少） | **人** | 抓包里可能没有成功样本，推断不等于观测 |
| **接口语义（登录 / 任务 / 查询）** | **人** | 抓包里没有任何字段说明这件事，只能靠需求上下文 |
| **签名算法** | **人 + 逆向** | 形态给不出算法；属解混淆域 |
| 复现产物的**内联** | 自动 | 产物是声明给出的文件，展开方式固定 |
| 复现产物**是否消掉待办** | 自动 | 判据是 `verified` 的有无，不是人的口头确认 |
| **桩响应的取值** | **人** | 真实接口返回什么形态，只有抓包和实测知道；桩不猜 |
| 判定逻辑的**回归验证** | 自动 | 桩会话按预设响应跑一遍，比对预期成败 |
| **验证证据（against / input / expect）** | **人** | 只有人知道产物是对着哪份抓包的哪个端点验的 |
| **响应取值的路径** | **人** | `data.token` 还是 `result.accessToken`，得看真实响应 |
| **路径参数取值** | **人** | 路径 id 每次调用都不同，工具猜不出来，也不该猜 |
| **第三方令牌的取值** | **人** | 抓包里只有产物没有算法，只能由操作者从浏览器取出后经 `env:` 注入 |
| 第三方令牌的**归属判定** | 自动 | 哈希相等可判：把第三方响应里所有长串建索引再查业务字段是否命中 |
| 值的**来源判定**（更早的响应里有没有同一个串） | 自动 | 判据是"同串出现过"，方向由 `startedDateTime` 决定，不看数组下标 |
| 条目**先后** | 自动 | 判据是 `startedDateTime`；数组下标不携带时间信息（实测 ProxyPin 是倒序） |
| **"同长候选"算不算线索** | **人** | 长度与形态相同只说明"像"，来源未证实，工具只负责点名 |
| 静态资源里**有没有源码线索** | 自动 | 判据是后缀与 mimeType，可判 |
| 接口的**编码族**（GET / urlencoded / JSON / multipart） | 自动 | 判据是包装函数写死的 `Content-Type`，且与抓包观测逐个吻合 |
| 内嵌源码里的**凭证** | 自动 | 按长度与字符集掩码；这是降噪与防误贴，**不是安全边界** |
| **字段的生成规则**（随机数 / 时间戳 / 账号派生） | **人** | 源码能给出规则原文，但"这段代码有没有真的跑到"仍要人确认 |
| 骨架拼装 | 自动 | 范式固定 |
| 凭证脱敏 | 自动 | 字段名可判 |

## 反模式

**把整份 HAR 丢进代码生成器。** 这类工具（`har2requests` 等）不做筛选，产出的是整个
抓包的代码，噪声远大于信号。正确顺序是先盘点、再筛接口、最后只对筛出来的两三个接口生成。

**用假值填签名参数。** 见上文核心判据。生成的骨架必须让这类参数抛错，而不是返回一个
`"0" * 32`。

**把回填当成完成。** 回填只把「没有实现」换成「有一个没人验证过的实现」。
若回填即消待办，清单会在第一次回填后变成空头支票——**而清单一旦失信，
后面所有明确的待办都不再有人认真看**。所以无证据的回填必须换成另一条待办，不是删掉一条。

**把复现产物内联成计划里的一段字符串。** 内联字符串无法 review、无法独立测试、
diff 出来是一坨转义。产物必须是仓库里一个真实文件，由生成器读进来展开。

**让自检永远说「通过」。** 没有反例的自检等于没有自检。验收方式是改错一位期望值，
它必须报不一致并以非零码退出；只覆盖正例的自检，会在产物悄悄坏掉时继续报绿。

**用退出码判断骨架的成败。** 生成的 `main()` 某一步失败时仍然返回 0——
它只在「没配账号」和 `NotImplementedError` 时返回非零。拿退出码当结论，
等于把「脚本没崩」当成「业务成功」，正是本流水线一直在防的那类静默失败。

**从抓包里抄凭证进脚本。** Cookie、Authorization、token 的值一律不落进脚本正文，
只保留参数名。账号走环境变量，会话凭证走登录捕获 + 状态缓存。

**直接复制公开脚本仓库的代码。** 青龙类脚本仓库普遍自述"搜集自公开互联网或由 AI 生成"，
多数没有 LICENSE 或来源不明。它们的正确用途是**接口形态的参照物**——看同一平台的签到
接口长什么样、参数命名习惯如何，而不是拿来当代码。

**对 multipart 一刀切拒绝，或一刀切生成。** 判据是"有没有 `filename` part"，不是
"是不是 multipart"。带文件字段的 part 内容无法从 HAR 可靠还原，明确拒绝比生成一个错的强；
**纯文本** multipart（零个 `filename`）则可以正常生成——`requests` 传
`files={name: (None, value)}` 就产出文本 part，boundary 由客户端生成，服务端只按
`Content-Type` 里的 boundary 切分。判据的具体形式是盘点输出的 `multipart_file_parts > 0`。

**探针只看 multipart 的结构化字段。** ProxyPin 对 multipart 一律给空的结构化 `params`，
字段只存在于请求体原文里。只读结构化字段，`token` 这类每次都在变的 part 就进不了
易变参数候选，计划作者也就不知道它每次都变——**盘点结果看起来完整，其实是空的**。
修法是从原文的 `Content-Disposition` 里取 part 名与值，带 `filename` 的单独计数。

**声明字段写了但没人读。** 计划模板里存在某个字段，生成器却从不读它——实测
`on_failure` 就是这样：模板写 `abort`，作者以为声明了"失败即中止"，实际每个步骤失败后
照跑不误。**这比没有这个字段更坏**，因为作者已经相信它生效了。修法三步：加取值校验
（非法值直接拒）、把行为真正写进 `run()`、加测试证明它改变了输出。推广成通则：
**计划 schema 里的每个字段，都要有一条测试证明它改变了生成结果。**

**只校验 HTTP 状态码。** 见「两个静默出错点」。业务码型接口下，这等于没有校验。

**拿数组下标当时间先后。** 实测 ProxyPin 导出的 `entries` 基本是倒序且非严格，
按下标读出来的时序图方向恰好相反。这类错误不报错、不自检、看起来还挺合理——
**一份方向相反的证据比没有证据更坏**，因为它会被当成结论用。

**把 `later` 和 `shape` 当成"找到了来源"。** 前者是值被发出去之后才在响应里出现，
后者只是长度和形态撞上了。两者都容易被读成"来源确认"，而它们恰恰是最需要人去查的
两类线索。工具把它们单独列出来，就是为了不让它们混进 `origin` 的计数里。

**按域名过滤把回显和回声一起过滤掉。** `--from` 只能区分"来源是不是你要的域名"，
不能拿去筛"值有没有被回显"——把正交的两件事合成一件，结果是 `echo` / `later`
被误标成 `other`，而这三种在报告里长得都像"没找到来源"。

**把同一判据在工具里写两遍。** 见「工具的两半互相打架」。新加一条：解析 multipart
原文、判定时间先后这类逻辑，必须复用 `har_probe` 里已有的实现（`multipart_parts` /
`entry_time_key` / `sorted_indexed_entries`），不能在第二个工具里再写一份。
两处实现一定会在某次修改后分叉，而分叉的表现是两份报告互相矛盾。

**用字符集把 JWT 切断。** 见「字段溯源」第五条。这类错误的形态是"工具能跑、报告完整、
结论为空"——命中数从 37 掉到 3 却没有任何报错。**凡是"提取一串东西"的正则，
都要问一句：真实样本里会不会有点号 / 等号 / 补位这种被漏掉的字符。**

**把内嵌源码当静态资源整体折叠。** 折叠是对的（它不是接口），但折叠之后必须还有一条
**去源码里搜**的路径，否则整类证据消失且不留痕迹。见「内嵌源码」。

**在写"看不出生成规则"之前，没去抓包的内嵌源码里搜过字段名。** 这条与上一条是同一件事
的两端：前者是工具的默认值问题，后者是使用者的动作问题。判据很简单——
**写下"看不出"这三个字之前，先回答"我在哪些材料里看过"。** 回答不出材料清单的
"看不出"，实际是"没去看"；而它会被下游当成一条结论使用。

**拿整串去查一个被包了一层字段。** `Bearer <jwt>` 直接查必然 miss，而 miss 会被读成
"没有来源"。判据是"同串出现过"，不是"整个字段值逐字相等"。

**把 `benign` 写成只比值。** 服务端真报 500 时会被当成"今天签过了"咽下去。

**工具的两半互相打架。** 实测踩到：计划模板按结构剔除了 10 个协议层产物，
生成器的待办清单却把同一批端点报成"未被任何 step 使用——确认是漏了还是不需要"。
**同一个判据在工具里存在两份实现，就一定会漂移。** 修法是让两处共用同一个分类函数，
而不是各写一遍。这条对所有"生成 + 校验"配对的工具都成立。

## 交付物必须自带的边界声明

这条流水线的每一段产出的都是**识别能力**，不是**绕过能力**。识别出"这个接口有签名"
不等于"可以复现它"；识别出"这里用 Cookie 鉴权"不等于"可以伪造 Cookie"。

因此交付物必须显式写清不覆盖什么：不复现签名算法、不绕过平台的访问控制与风控、
不处理未授权目标。缺了这句声明，读者会把"看清楚状态"误读成"改变状态"。

**边界不只是免责声明，它决定代码形态。** 实测需求方给的边界是"允许自动化签到、
不允许 DDoS"——落到产物上就是：所有骨架都是顺序单账号请求、固定账号间隔、零并发，
并且 README 里要明写"不要把它改成并发循环"。把请求数放大到压测量级就跨过了这条线。
所以交付物里的边界声明必须和代码结构对得上，对不上的声明是空的。

同一条判据也管到依赖：**生成器不替人决定要不要调外部进程。** JS 复现产物需要 node，
计划里不写 `allow_external_runtime: true` 就直接拒——能力越界必须由声明显式打开，
工具的默认值只能是「不越界」。

还有一条是**材料边界**，不是能力边界：字段溯源要读**响应体**，而降级夹具刻意丢掉了
响应体。所以溯源只能在真实抓包上做，与抓包同属本地。**"没有材料"和"没有来源"是两件
事**，工具在池子残缺时会显式区分，读报告的人也得区分。

## 与技能层的分工

骨架落在 `automation-script-dev-py` 的既有模式上：账号加载对应 P3、登录与状态缓存对应 P4、
请求重试对应 P6、日志脱敏对应 P11。骨架只铺主干，代理接入（P1）、防封与随机化（P2）、
通知渠道（P12）、项目归集与 README（P10）由人在骨架上叠加。

## 输出

- 接口地图（`--json` 为机器可读，默认脱敏）
- 字段溯源报告：值 → 来源域名 + 端点 + 时间差（只出长度与哈希，不出明文）
- 内嵌源码检索：可读资源清单 + needle 命中的资源/偏移/上下文（长不透明串已掩码）
- 意图声明 `<name>.plan.json`（可 diff、可评审）
- 脚本骨架 + 待人工完成清单
- 复现产物（人写在计划旁边，由生成器内联）+ 骨架自带的 `--selftest` 入口
- 桩会话验证：判定逻辑在预设响应上的通过/失败结论（不发真实请求）
- 合成夹具（保形脱敏，可进仓库做回归）

命令见 `AI-USAGE.md` 的「路由自动化」一节。
