# 验证阶梯

用途：在你准备宣布"做完了"的时候读，或者你需要为复核者定义"做完"的时候读。
它给出主张阶梯、证据链，以及每种交付形态在被承认之前必须拿出什么。

业余改动和可用交付物之间的差别就是验证。"它能组装"和"日志很安静"都不是验证。

## 主张阶梯

每一级都是更强的证据。爬到任务要求的高度，并且**明确说出你爬到了哪一级**。

| 级 | 主张 | 需要的证据 |
|---|---|---|
| 0 | "文件被改过了" | 目标位置的字节级差异 |
| 1 | "结构完好" | 结构差异工具：类/段集合一致、关键标志位漂移为零、未改动的部分逐字节相同 |
| 2 | "能构建、能签名" | 签名校验通过，并附上原始命令而不是一句"ok" |
| 3 | "能加载、能运行" | 进程存活，运行日志没有致命特征串 |
| 4 | "目标行为变了" | 被观测到的那个具体行为确实变了（走到了那个界面、观测到了那个请求、确认了那个状态） |
| 5 | "没有别的回归" | 相邻功能被逐一走过：资源加载、播放、列表、登录、设置 |
| 6 | "机制被证明了" | 关于**为什么**的独立证据——例如某个子系统从未初始化，所以它的域名从未被解析；或者它从未在私有目录下建立自己的工作目录 |
| 7 | "**分发出去的那份**就是被验证的那份" | 把已发布的文件重新下载回来，哈希与你测过的本地构建比对 |

**第 3 级是任何交付物的最低线。第 4 级才支撑"这次改动解决了问题"这一主张。第 5 级是交给用户
之前。第 6 级用在主张是"整个子系统死了"而不是"这一处现象消失了"的时候。第 7 级用在交付物离开
你的机器时——上传会截断，构建流水线里的某一步会重新签名，而下载的人无从知道。**

## 零改动对照规则

在把责任归给改动之前，先做一个对照：**同一条流水线，零改动。**

- 对照失败 → 是你的流水线、环境或设备的问题。停止调试改动本身。
- 对照通过、改动版失败 → 改动被牵连。逐文件回退，做二分。

**每当有东西意外失败时**做这件事，并且每个项目至少做一次。

## 结构验证（把它自动化）

每次编辑之后跑结构差异工具。期望恰好是：

```text
only_in_A=0   only_in_B=0
关键标志位不匹配: 0
```

一个重要的保留意见：**这类检查看不见代码项损坏。** 一次全树往返可以过掉每一张表检查，
然后在运行时崩溃。过掉这个检查是**必要而非充分**。

能看得更远的检查——指令长度审计、等长替换的盲区、验证器层面的合法性——要用在
宣布改动落地之前。

同时确认你改的正是你想改的、且没有多改：

- 把改过的产物反解回来，检查目标位置。
- 在可行处，把未改动的部分与原件逐字节比对。

## 运行验证

```text
清空日志 → 启动目标 → 隔一段时间采一次存活状态（间隔开）→ 扫日志里的致命特征串
```

**存活状态要采两次、且间隔开。** 单次读数抓不到崩溃循环里死掉又起来的程序。

**只有日志往往不够。** 如果目标安装了崩溃处理器，调用栈永远到不了系统日志。一个只留下
"未捕获异常 时间: …"、没有栈的退出进程，**是崩溃了**——把它当失败处理，不当噪声。

## 行为验证（最容易被跳过的一段）

能启动不能证明任何关于你改动的事。去**走它**。

- **现象消失类改动** → 打开所有出现过该现象的界面。确认它不在，**并且**确认那些界面仍然可用。
  用**三个独立信号**，不是一个：界面看起来对、相关组件的日志标签消失、以及它从未建立自己的
  工作目录。一个静默地填充失败的组件，看起来和一个从未初始化的组件一模一样，
  只有后两个信号能把它们分开。
- **门禁类改动** → 把受门禁的流程从头到尾走一遍。
- **超时 / 上限类改动** → 去触发它。
- **数据类改动** → 停掉进程、清掉 / 重写那个值、冷启动、复查（证明它不是内存里的假象）。

**然后测邻居。** 现实中最常见的回归，是一次改动修好了它的目标，却安静地弄坏了不相关的东西：

- 图片 / 封面渲染吗？
- 音视频播放正常吗？
- 列表能滚动、能翻页吗？
- 登录 / 会话还有效吗？
- 设置界面能打开吗？
- 下载还能启动吗？

这正是"一个通用图片卡片改动把所有封面都干掉、而广告照常显示"发生的方式。

## 截图纪律

每个主张都抓改前 / 改后截图。文字描述不是证据；一张"没有该现象的界面"截图，
配上对照构建里"有该现象"的那张，才是。

## 报告

```text
构建：      <路径> <sha256>
基线：      <原始文件名 / 版本>
改动：      <文件 → 改了什么>，一行一条
结构：      结构差异工具结果（逐文件）
签名：      用 <确切参数> 校验通过；贴原始命令，不要只写 "ok"
环境：      <设备型号 / 系统 / ABI / 是否提权>
运行：      存活状态在 N 秒内稳定；无致命特征串
行为：      <走过的界面>，<改前 / 改后>
回归：      <检查过的相邻功能>
分发：      <发布位置> 重新下载，sha256 与受测构建一致
到达级别：  0..7
残留：      <没有修好什么，以及确切原因>
```

**把残留写清楚。** "X 仍然存在，因为它随界面的主数据载荷一起下发，而在传输层抑制它会把整个界面
带崩"是一个有用的、诚实的结果。默默省略它不是。

**分开两个受众。** 产物交给最终用户；分析报告交给要这项工作的人。面向用户的说明保持中立务实——
名称与版本、安装前提、签名冲突警告（签名者不同意味着旧安装必须先卸载）、校验和、以及一行
范围与免责声明。把机制、改动点和推理留在你自己的报告里，不要写进最终用户打开的那个文件。

## 反模式

- 从一次成功的组装就宣布成功。
- 从安静的日志就声称"没有该现象"，而组件本来也可能什么都没打印。
- 只启动一次、不走功能，就下结论。
- 拿模拟器的结果当设备的结果引用。
- 报告修好了某个功能，却没检查相邻功能。
- 隐藏已知的残留失败。
- 把一个**未改动的原件**也有的失败归咎于自己的改动——先跑零改动对照。
- 当交互可能从未触发时，接受界面自动化的结果作为证明：要校验字段内容、找真实的请求，
  而不是只看屏幕。
- 在检查服务端证书之前，就把一个只影响某功能的网络错误当成改动问题。
