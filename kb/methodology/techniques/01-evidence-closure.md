# 证据闭环

用途：让每条结论都能被独立复核。这是本套件所有分析类技能的公共底线。

## 节点执行口径

每个分析节点（无论大小）都用同一套口径描述，缺一项就说明该节点还没做完：

```text
入口信号：什么现象让你走到这一步
打点动作：具体做了什么（命令 / 函数 / 观测点）
成功标志：什么现象说明这一步成功了
下一跳：  成功后该去哪里
证据：    落在哪个文件、哪一行、哪个地址
```

**没有产生下一跳的入口，要把失败样本写进"已尝试/已排除"，说明卡在哪。** 这比"尝试过但没结果"有价值得多——它防止后续重复走同一条死路。

## 证据分层

| 结论类型 | 必须绑定的证据 |
|---|---|
| 静态结论 | 类名 / 方法签名 / 相对虚拟地址 / 偏移 / 字符串 / 交叉引用 |
| 动态结论 | Hook 点 / 参数 / 返回值 / 时间戳 |
| 改写结论 | 原文件与候选文件的 SHA-256 + diff + 验证输入与结果 |
| 补丁结论 | 原始字节 / 新字节 / 签名方式 / 安装启动结果 |

**不能以"构建成功"代替"行为验证"。**

## 三态与恢复点

长任务必须能回答"现在到哪了、下一步做什么"，而不是靠重读对话记录。

| 状态 | 含义 |
|---|---|
| CONTINUE | 还有可执行的下一步 |
| DONE | 目标达成，证据齐全 |
| EXHAUSTED | 已尝试的路径都走完，无可行下一步 |

配套的恢复点至少包含：

- 目标与当前阶段
- 已完成的步骤与各自证据位置
- 已排除的路径（**含排除原因**）
- 下一步动作列表
- 未解决的开放问题

**纪律**：不要把"等待人工确认"当作状态；无人值守执行失败时，记录证据并切换路径。

## 反注水纪律

沉淀知识时，"没有增量就不硬改"。

- 一次任务没有产生新的通用技巧，就只留案例记录，不往知识库塞内容。
- 只记录**可复用的发现、坑点、工具选择经验**，不记录命令流水账。
- 每条沉淀要能回答"下次遇到什么信号时该读它"。

## 交付检查

交付前逐项确认：

- [ ] 有实质产物（脚本 / 还原版 / 报告 / 路由结论），不是只有对话说明
- [ ] 证据已落盘到约定目录
- [ ] 原始文件未被覆盖，修改前已备份
- [ ] 每条结论附路径 / 哈希 / 命中信号 / 验证命令
- [ ] 不确定项与已知限制已显式写出
- [ ] 未实际执行的验证（如长时间稳定性测试）没有被写成"通过"

## 可验证事实清单

交付时附一份事实清单，供改版或同类样本回归：

```markdown
- [ ] <事实1>
- [ ] <事实2>
```

全部通过 → 结论仍成立；部分通过 → 变化的那几条就是本次工作范围；全部不通过 → 目标大改，但通过过的条目仍是有效不变量。
