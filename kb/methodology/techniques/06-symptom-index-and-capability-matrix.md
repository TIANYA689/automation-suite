# 症状索引与能力矩阵

用途：设计或维护知识资产的**查找层**时读这一篇。它回答两个问题：
**"卡住的时候，怎么让下一步只跳一次"**，以及**"这条能力到底有多可信，怎么写才不夸大"**。

**强度约定**：`observed` 有实测，`inferred` 由机制推出，`unverified` 为转述或假设。

## 症状索引：把"卡住"变成一跳

**症状索引是查找层，不是知识本身。** 它只装两列：**你观察到什么 → 先读哪一篇**。

设计要点：

- **粒度是"一个可观察到的具体信号 / 报错 / 现象"，不是"一类任务"。**
  反例：`动态分析 → 某文件`。正例：`段错误且故障地址极小 → 某文件`、
  `库自称的名字与文件名不符 → 某文件`。
  前者的信息量等于零，因为"我在做动态分析"这件事你本来就知道。
- **去处要具体到小节**，而不只是文件名。
- **必须与入口文档一起加载**，所以它放在入口里，而不是放在被指向的正文里。
  这就是"一跳可达"的含义：**识别失败不能变成两跳查找**——如果你得先打开一篇文档
  才知道该读哪篇，那这一跳已经白费了。
- **索引与正文分工明确**：索引只回答"去哪"，诊断步骤与细节留在被指向的正文里。
- **一致性要机器强制**：入口里的索引与被指向的文件之间不一致、或某个文件没被任何索引点名，
  都应当由脚本报错。手工对账一定会漂移。

**什么时候读症状索引，什么时候读案例**：**卡住时读症状索引**（它更快）；
**准备重做这类工作时读案例**（案例回答的是"什么序列产出了可辩护的结果、代价多少"）。
把这两件事混起来，两边都会变得难用。

## 能力矩阵：诚实记录"哪条有实测支撑"

一张能力矩阵至少要有五列：

| 列 | 内容 |
|---|---|
| 能力 | 一句话说清是什么 |
| 被证明了什么 | 一行，只说被证明的那部分 |
| 状态 | 见下面三档 |
| 强度 | `observed` / `inferred` / `unverified` |
| 证据位置 | 落在哪个文件 |

**状态三档，中间那档是关键：**

| 状态 | 含义 |
|---|---|
| `ok` | 在真实目标上跑通，结果已记录 |
| `partial` | **一个决定性步骤没跑**——通常是安装、启动，或第二个独立产出者 |
| `blocked` | 依赖本套件不随附的东西；或者此处两个方向都不是证据 |

**强度三档**沿用统一口径（见
`kb/methodology/techniques/04-coverage-and-limits.md`），`observed` 严格保留。

### "工具被测量"与"路线被测量"要分开

这是矩阵最容易写错的地方，靠**状态 × 强度的组合**来区分：

- **`partial` + `observed`** = 工具能用，**路线没跑通**。
  实例：某个改写工具"写入落盘、脱离后仍然存活，但目标仍在同一位置死"——
  工具被测量了，路线没有。
- **`ok` + `observed`** = 端到端成立。

配套的失败模式警告，写进矩阵旁边：

- **工具跑了不等于工具对。**
- **自信的段落不等于 `observed`。**
- **`unverified` 是"此处无证据"，不是"反证"。**

### "证据够不到你的情形"怎么读

给读者一张对照表，比单纯标强度更有用：

| 你看到 | 该怎么用它 |
|---|---|
| `observed`，但你的目标形态不同 | 当成"先试的理由"，不是保证 |
| `inferred` | 预算一个便宜实验，把它变成 `observed` |
| `unverified` | **不要**引用本套件作为支撑 |
| `blocked` | 不要即兴造路线，先点名缺的那个依赖 |

## 路线清单：覆盖边界单独成篇

路线清单分三段，第三段最容易被忽略：

1. **有已验证机制覆盖的**——每条后面挂命令与输出。
2. **有文档但只是推断的**——机制写清楚了、端到端没测过，当"带边界的线索"用。
3. **本套件不分发的依赖**——**每一项是一道栅栏，不是一句提醒**。
   栅栏的意思是：没有它，这条路线根本走不通，所以必须在流程开始前点名。
4. **不覆盖的**——明说不覆盖，而不是即兴发挥。

## 三者互引，各答一个问题

| 资产 | 回答 |
|---|---|
| 症状索引 | 下一步该读哪一篇 |
| 能力矩阵 | 这条能力有多可信 |
| 路线清单 | 覆盖边界在哪 |

三者的存在价值在于它们**不重复**：索引不解释机制，矩阵不讲步骤，清单不列症状。

## 案例库：把一次收敛写成可复用的东西

- **可复用模式**只保留"能无改动迁移到另一个目标"的那一条。
  需要本目标特有名字的，属于执行链，不属于模式。
- **执行链必须含死路**：错误的转向 + 杀死它的那次测量。缺了这一段，
  案例就是成功故事，而成功故事教不会任何能撑过下一次意外的东西。
- **案例与坑点目录刻意不重叠**：案例用编号指向坑点，不复述失败。
  复述会让同一失败模式在两地漂移，然后互相矛盾。
- **回写清单是完成判据**：点名"应该回写到哪些文件"。
  **没有回写清单的案例是日记**——它让知识留在作者身上，而不是留在仓库里。

## 本套件里的对应物

| 上游概念 | 本套件的落地 |
|---|---|
| 症状索引 | 各 `kb/<领域>/techniques/kb-index.json` 的 `signals`；技能内的问题→去向表 |
| 能力矩阵 | `kb/methodology/techniques/04-coverage-and-limits.md` 的覆盖分栏与强度标签 |
| 路线清单 | 同上篇的「不覆盖」与「不分发的依赖」两节 |
| 案例库 | `templates/case/`（`state.json` + `ai_manifest.json`）与 `kb/ai-findings/findings.jsonl` |
| 一致性强制 | `scripts/misc/check_index.py`（索引完备性）、`scripts/misc/check_routing_drift.py`（路由漂移） |

**一条来自上游的自我指认**：它的检查脚本会**全量打印豁免项并计命中次数**。
理由很实在——**豁免项是最容易变成漂移藏身处的地方**。
