# 第三方脚本的结构盘点

用途：把"别人的脚本"变成可复核的结构证据——在读懂任何逻辑之前，先知道
**有哪些文件、哪一类、多少行、在哪些行命中了什么**。

## 为什么先盘点再阅读

直接从头读一个不熟悉的脚本，会在两件事上白白花钱：读一个 12000 行的压缩文件，
或者把 `node_modules` 里的依赖当成作者的手笔。盘点把这两类代价**在阅读之前**消掉。

盘点的产物不是"结论"，是**证据**：文件清单、类型、行号。结论要靠回看这些证据得出。

## 可读性分类：五类与它们的失效模式

| 类型 | 判据 | 阅读策略 |
|---|---|---|
| 可读 | 未见混淆或打包特征 | **范本只能来自这里** |
| 压缩 | 最长行 ≥ 1000 字符、或平均 ≥ 400、或打包产物命名 | 只当信号，不提炼写法 |
| 混淆 | `_0x` 型标识符成片、连续转义串、超长 base64 + `eval` | 先解密再回来（`js-script-deobfuscator`） |
| 静态库 | 位于 `vendor/` `lib/` `dist/` 等目录 | 是别人交付的成品，不是写法 |
| 读不出 | 非 UTF-8 文本 | **对它的能力矩阵无结论** |

分类是启发式，所以每条结论都要带**线索**（"最长行 3400 字符"比"压缩"有用，
因为下一个人可以据此推翻它）。

### 两个已知的判定陷阱

**陷阱一：优先级不是"或"**。一个放在 `vendor/` 里的混淆文件，该报"混淆"。
"它是别人交付的库"这件事，不足以说明"它没有隐藏规则"。
所以分类要定优先级，而不是并列打分。

**陷阱二：用源码正则判"交付形态"会大面积误判**。曾经用 `^#\s+\S` 判"随附文档"，
结果是**每个带注释的 Python 文件**都命中——一条把注释误认成交付物的假阳性。
配套文件（README / `.env.example` / 依赖清单）的证据在**目录清单**里，不在代码文本里。

## 为什么不导入、不执行

Python 走 `ast.parse`，JS 走正则。理由不是洁癖：

- 第三方脚本的模块级代码可能建文件、连网、读凭据、`sys.exit`。
- 拆解的价值在于"我看了它"，不在于"它跑了"。
- 一旦执行，"没执行"这个承诺就无法复核——而它是唯一能让拆解进入不受信任环境的前提。

**"不执行"不等于"跳过"**：诱饵脚本仍要出现在清单里、仍要做语法解析。
把"没执行"做成"没看见"，是另一种失败。

## 能力维度：按"变化频率"设计，不按"重要性"

维度表（检测维度 / 风险规则 / 配套文件）应当是**数据**，引擎是**逻辑**。
拆开的标准不是行数，是变更频率：加一个检测维度只改表，引擎不动。
放一个文件里，每次加维度都要动一个千行文件。

维度要覆盖**基础设施**而非业务动作：配置、环境变量、账号加载、登录凭证、
请求封装、超时、重试、代理、多阶段协议、并发、锁、节奏、循环上界、批次可观测、
日志、脱敏、缓存、通知、设备身份、签名、验证码、邮箱、接码、命令行、定时、交付文件。

**业务动作（签到、领取、下单）不进维度表**：它们随站点变化，抽不成通用维度。

### 关键词型检测的系统性偏差：只认一种写法

**这是第一次在真实脚本上跑才暴露出来的**，一个脚本同时踩中三处：

| 维度 | 表里只认 | 真实脚本里是 | 后果 |
|---|---|---|---|
| 多账号加载 | `ACCOUNT_SEP(ARATOR)` | `ACCOUNTS = [...]` | 判成"没有多账号" |
| 配置集中 | `class Config` | 连续四行模块级常量 | 判成"配置散着" |
| 日志输出 | `logging.getLogger` | 自建 `def log(msg)` | 判成"没有日志" |

根因不是"漏了一条正则"，而是**维度定义时想的是"我会怎么写"，不是"别人会怎么写"**。
这三处漏报都在同一个方向：只认得标准库 / 框架的写法，认不出**自建的同名设施**。
而自建设施恰恰是这类脚本的主流——它们跑在面板里、输出被面板捕获，
所以不用 `logging`；配置写在脚本顶部，所以没有 `Config` 类。

判据：**加维度时先问"这个维度在真脚本里最常见的三种写法是什么"**，
把三种都写进 `regexes`，而不是等踩到再补。
补的时候注意别把判据放宽到失去区分度——`config` 那条要求**连续两行**才认，
单个 `MAX_RETRIES = 3` 到处都是，认它等于让这个维度永远命中。

#### 另一半：认了"标准库写法"，还会漏"另一种命名"

| 维度 | 表里只认 | 真实材料里是 | 后果 |
|---|---|---|---|
| 敏感信息脱敏 | `def mask*` + 裸词 `脱敏` | `def redact(value: str)`（`har_probe.py:104`） | **真证据漏了**，反而命中 `:599` 那句 `"输出已脱敏（--no-redact 可关闭）"`——提示语被当成实现 |

这一次是在**自扫本套件自己的代码**时发现的，所以它不是"第三方脚本的特殊性"，
是规则的通用缺陷：`mask` 与 `redact` 是同一件事的两种命名，表里只写了一种。

还有一层更隐蔽的：**裸词与结构化正则的失效方式不同**。

- 结构化正则（`def\s+mask`）命中的必然是代码，写错只会漏。
- **裸词（`脱敏`、`进度`、`断点`、`多账号`）命中的可能是"给人看的字符串"**。
  `print("输出已脱敏")` 是**字符串字面量**，不是注释——散文过滤按纪律不剔它
  （`"User-Agent"` 就是实打实的协议证据，剔了就是静默假阴性）。
  于是裸词既要防漏，又要防"提示语被当成实现"。

判据：**裸词必须锚到代码位置上**——`def\s+\w*(?:脱敏|打码)`，不让它自由浮动。
换句话说，**关键词的数量不是判据，关键词所在的位置才是**。

#### 第三半：跨语言——声明覆盖 5 种语言，正则只写了 1 种

前两半都是"同一种语言里的命名差异"，这一半是**语法差异**：

| 维度 | 表里只认（Python 写法） | JS 里是 | 后果 |
|---|---|---|---|
| 节奏控制 | `time.sleep(` | `setTimeout(` / 自建 `delay(ms)` | 判成"没有节奏控制" |
| 重试与熔断 | `MAX_RETRIES` / `maxRetries` | `maxAttempts` + `for (let attempt = 1; …)` | 判成"没有重试" |
| 超时设置 | `timeout=` | `timeout: 10000`（对象字面量用**冒号**） | 判成"没设超时" |

实测来源：**本仓库自己的可读 JS**（`slider_captcha_manager.js`，116 行）。
它是第一个跑得通 JS 侧规则的可读 JS 样本——此前两轮真材料里唯一的 JS
恰好是加密载荷，所以 JS 侧的覆盖度一直只是**推断**，这三处是第一次实测。

关键区别：这不是"少写了一个别名"。`timeout=` 与 `timeout:`、`while True` 与
`while (true)`、`def mask(` 与 `function mask(`——**名字相同，形状不同**。
所以补法也不一样：命名差异可以多写几个别名，**语法差异必须按语言各写一条**。

根因一句话：**`langs` 声明与 `regexes` 实际覆盖不是一回事。**
`ALL_LANGS` 只表示"这个维度对所有语言都适用"，**不表示**"每条正则对所有语言都命中"。
声明覆盖 5 种语言、实现只写 1 种，与"报告里的断言比判据强"是同一个病——
**维度声明不能比正则强**。

核对方式（加维度、或改 `langs` 时顺手做）：把该维度的每条正则按语言过一遍，
问"**这门语言里最常用的三种写法，有几条能命中**"。

同一族的第二个坑：**解析失败会让"没材料"伪装成"没命中"**。
Python 文件 `ast.parse` 失败时拿不到语法树，文档字符串就漏过散文过滤 →
关键词在叙述里出现也被当成证据，**能力矩阵偏多**；同时符号表为空，结构清单不全。
所以"读得出"（UTF-8 可解码）与"解析得了"（语法树可用）必须**分开报**。

### 结构性裸词匹配的是「出现」，不是「能力」

同一批真材料上还暴露了另一类：**正则写的是一个"到处都是"的语法形状**。

| 维度 | 表里只认 | 真实材料里是 | 后果 |
|---|---|---|---|
| 批次可观测 | 裸 `batch` | `batch_size = random.randint(2, 3)`——并发批量大小 | 判成"有批次可观测" |
| 常驻循环 | 裸 `while True` | 一个带 `break` 的查找循环 | 判成"无界循环" |

判据是一句话：**这个词在任意上下文出现都成立吗？**

- `timeout =` → 成立（任何 timeout 都是 timeout），可以裸。
- `batch` → 不成立（`batch_size` 不是批次可观测），必须要求语境。
- `while True` → 出现是成立的，但**"无界"不成立**——见下一节。

### 报告里的断言不能比判据强

`while True` 与"无界"之间隔着一个 `break`，正则够不着。这里有两种做法：

- 硬猜：加一条"后面 N 行内没有 `break`"的启发式。**不做**——嵌套循环的 `break`
  会被当成本层的，制造新的假阴性，而假阴性在报告上看不见。
- **如实说正则能看见什么**：标签从"无界常驻循环"改成"`while True` 常驻循环"，
  说明改成"正则看不出有没有 `break`，**必须回原文确认**"。

选后者。**够不着就别断言**——报告是给人照着做的，一句"无界"会让人
去改一个本来就正常的循环，而一句"回原文确认"只花他十秒钟。

### 读了但看不进去：加密 / 打包载荷

压缩产物**美化一下就还原**，加密载荷（自解密脚本的密文段、`exec(base64…)` 的载荷）
**美化器对它无效**，得先拿到解密方式。两者共同点是：**关键词彻底看不见**。

实测：一个 143 KB 的 JS 是自解密脚本，外层几十行 `aes256GcmDecrypt` + 140 KB 密文，
25 个维度命中 **0** 个——而报告原本一个字都不说。读者会把"关键词在密文里"
读成"它没有这个能力"。

判据可以很干净：**单行占全文的比例**。实测不可读文件是 82%–99%，可读文件 1.3%。
所以"这个文件的 0 命中不代表没有能力"必须**被说出来**，
和"没有材料"「没有命中」并列成三件事。

> 这与 `har_probe` 把 `.js`/`.css` 折叠掉是同一形态的失效：
> **工具没错，是没去那一类材料里看。** 而"没去看"与"看不出"在报告上长得一样。

### 证据取值：优先取可读文件里的那一处

一个维度可能在多个文件里命中。展示时**优先取可读文件里的命中**：
结论是据可读代码下的，却拿压缩文件的行号当证据，读者会以为范本在那段不可读的代码里。

### 只报首个命中

报告要的是"有没有、在哪"，不是全量出现次数。行号清单越长越没人复核。

## "没命中"与"没材料"必须分开报

这是本类工具最容易出错、也最贵的一处：

| 情形 | 正确表述 | 错误表述 |
|---|---|---|
| 目录为空 / 后缀不在范围 | 没有材料 | 未发现可复用内容 |
| 文件非 UTF-8 | 对它无结论 | 它没有这个能力 |
| 只在压缩/混淆文件里命中 | 是信号，不是范本 | 命中该维度 |

把"没去看"写成"看不出"，是本套件反复踩过的坑（同 `har_source` 的负面结论纪律）。

## 片段掩码的分寸

- 长不透明串、邮箱、手机号：输出前替换。
- **凭据类命中只报行号，不报片段**。报告会被贴进对话、写进笔记；
  片段里带真值，泄露就发生在"检查"这个动作里。
- 掩码是**降噪与防误贴，不是安全边界**：它挡的是顺手把真值抄进报告，挡不住刻意规避。
