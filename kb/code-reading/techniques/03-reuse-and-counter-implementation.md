# 复用判定与对照重写

用途：把"这个写法值得抄吗"从感觉问题变成四档可判定的事，并把"我来写会怎么做"
变成一张能交接的差异表。

## 为什么必须分档

**"值得复用"和"能跑通"是两件事。** 一个跑得通的脚本可以同时包含值得抄的编排结构
和绝不该抄的凭据硬编码。不分档的"学习笔记"会把两者一起搬进来，
而搬进来之后，没人会再回头查第二遍。

分档的成本是几分钟；不分档的成本是下一次泄露或下一次线上事故。

## 四档的判定线

| 档位 | 判定线 | 典型 |
|---|---|---|
| 直接复用 | 换目标站点仍成立 + 本项目已有 Pattern 覆盖 + 无站点专属名字 | 超时、退避结构、配置双源、脱敏、原子写 |
| 改造后复用 | 思路成立，但接口形状或运行环境前提与本项目不同 | 账号解析、通知渠道、代理接入、日志形态 |
| 只可借鉴 | 实现与目标站点密钥/算法/字段绑定，或"聪明"来自对某系统内部的观察 | 签名、设备指纹、协议阶段划分、编排形状 |
| 拒绝吸收 | 降低安全机制、引入合规风险或不可控副作用 | 凭据硬编码（含写成环境变量默认值）、风控绕过、代理凭据进 URL、**会话凭据外发给第三方**、反调试 |

> **「会话凭据外发给第三方」单独列出来**，因为它比硬编码更隐蔽：源码里看不到任何密钥，
> 秘密是在**运行时**被送出去的——cookie jar 被掏成 dict，连同 token 一起 POST 给
> 某个打码/接码平台（实测样本 L1812-1826，目标是一个动态 DNS 域名）。
> 静态扫一眼源码"没看到密钥"就判它干净，正是这种写法最容易骗过的检查方式。

完整判据、升降档规则与逐项清单见
`skills/third-party-script-teardown/references/reuse-classification.md`。

### 与「吸收纪律」共用同一条判断线

上游吸收纪律的切法是问**"是搞清楚状态，还是改变状态"**：

- **吸收**：测量 / 记录 / 对照 / 回滚 / 结构归档 / 验证——让状态**更可见**。
- **不吸收**：降低安全机制、绕过校验、隐藏行为——让状态**更不可见**。

对象不同（仓库 vs 单个脚本），判断线是同一条。**不各写一套**。

## 拒绝吸收必须写进报告

"我看过它、我决定不抄"和"我没注意到"在下一个人那里是两件事。
报告里那一节允许为空，但为空时要写明"逐项检查过，无"——
**沉默的跳过无法与遗漏区分**。

## 对照重写：写差异表，不写重写版

"我来编写又会怎么做"的产物是**差异表**，不是另一份脚本：

| 维度 | 别人的做法 | 我会怎么做 | 为什么不同 | 依据 |
|---|---|---|---|---|

三条规则：

1. **每行必须有依据**。填不出 Pattern 编号的，说明这是个人偏好而不是工程结论——
   标成"偏好"，不要伪装成"更优"。
2. **不改写业务逻辑**。别人对目标站点的理解可能比通用规则更准；
   只对基础设施层下判断。
3. **能不动就不动**。差异表里没有"我全都会重写"这个选项。

## 知识回填：三档去处

拆解不产生知识库内容，只产生**候选**。

| 候选形态 | 去处 | 判据 |
|---|---|---|
| 能写成"当 X 出现时做 Y，用 Z 验证" | `kb/<领域>/techniques/` | 至少两个独立场景 / 可执行 / 去项目化 |
| 一句话结论、单条、可能只对一次 | `kb/ai-findings/findings.jsonl` | 有证据，通用性未证 |
| 只有本次目标才成立 | 留在报告里 | 删掉目标名就失真 |

**提案先于写入**：跨技能或跨领域改动走 `knowledge-architect` 的 CHECKPOINT。
本流程只负责把候选写成可检验命题并给出证据位置。

**反注水**：一次拆解没有产生新的通用技巧，就只留报告，不往知识层塞内容。
知识层的每一条都要能回答"下次出现什么信号时该读它"。

## 反模式

- 因为"跑得通"就整段照搬。
- 把拒绝吸收的项从报告里删掉，只留"值得学习的部分"。
- 复用候选里混进压缩 / 混淆文件的命中（那里面没有可读的范本）。
- 档位一栏全填"直接复用"——通常意味着没有真的分档。
- 对照重写表只有"我会怎么做"，没有"为什么不同"和依据。
- 为凑知识库条目把一次性结论升级成通用规则。
