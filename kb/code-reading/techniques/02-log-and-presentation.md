# 输出呈现与日志美化

用途：让**人**能扫一遍就用，让**下一个人**能复核。分两处落点——
工具/报告的呈现，和生成脚本的日志。

## 结论先行

读者第一屏要拿到结论，不是拿到过程。把结论放在 300 行之后，等于没写结论。

信息层级（自上而下）：

1. **一行结论**——这次拆解/这次运行得到了什么。
2. **口径**——扫了什么、跳过了什么、依据什么。
3. **分节证据**——结构、能力、复用、缺口、风险。
4. **提示与未覆盖**——没材料、没读的文件、没验的假设。

## 对齐必须按显示宽度

中文标签是**双宽字符**。`f"{'配置集中':<10}"` 补的是**字符数**，4 个汉字占 8 列，
于是它和 6 个汉字的标签在屏幕上差 4 列。

整列歪掉的表会被当成随手拼的输出——而"看起来不可信"和"不可信"，
在交接时的后果是一样的。所以：

- 按 `unicodedata.east_asian_width(ch) in "WF"` 计宽（CJK 与全角符号记 2）。
- 补齐走自定义 `pad()`，不用 f-string 的 `:<n`。
- 手写报告交给 Markdown 渲染对齐，不要在纯文本里手数空格。

## 控制台编码要能退，不能崩

制表符（`═ ─ ╭`）不在 GBK 里。直接 print 会抛 `UnicodeEncodeError`，
而一个因为终端编码崩掉的工具，会让人以为它本身有问题。

做法：先试 `"═─╭╰│├└".encode(encoding)`，编不出就整体退回 ASCII（`+ - |`）。
**同一份内容、两套画法**，而不是"高配版崩、低配版缺"。

## 机器可读与人读必须同源

`--json` / `--out` 与默认文本**渲染同一个报告对象**。各写一套的结果是：
JSON 里有的字段文本里没有，改一处忘另一处，两份输出慢慢互相矛盾。

## 诚实标签

- 每条结论带**分级**：`observed`（有行号/命令在背后）/ `inferred` / `unverified`。
- 每条启发式结论带**线索**（"最长行 3400 字符"），让读者能推翻它。
- 数字带**口径**："扫到 12 个"与"目录里有 12 个"不是一回事；
  跳过多少、为什么跳过，和被统计的数字一样重要。
- 负面结论要分类：没有材料 / 没命中 / 读不出，三者不能混成一句。

## 长度预算

- 工具输出：默认只列前 N 个文件，超出提示 `--top 可调`。
- 人读报告：正文 150 行以内。超了说明在复述过程而不是在给结论——
  细节挪进 JSON 证据文件。

## 生成脚本的日志

**本节不复制脚本日志规范。** 唯一事实源：

- Python：`skills/automation-script-dev-py/SKILL.md` 的 P11 / P11.1 / P11.2
  （状态卡片、汇总表、脱敏、线程安全日志）。
- JavaScript：`skills/automation-script-dev-js/SKILL.md` 的 P8.5。

读第三方脚本时要**额外**注意的两点：

1. **别人的日志形态常是反面教材**。每行裸 `print` 带完整 token 是常见写法，
   不要因为"它跑得好好的"就继承。
2. **日志是最容易被"以后再说"的一层**，而它恰恰是交付后唯一还在被人看的东西。
   在对照重写表里给它一行。

## 反模式

- 结论写在最后，或只有过程没有结论。
- 用"更优雅""更规范"代替可复核的证据。
- 断言全标 `observed`。
- 把 JSON 输出整段贴进报告充当分析。
- 表格靠空格手对齐，换台机器就歪。
- 终端编码不支持时印乱码或崩掉。
