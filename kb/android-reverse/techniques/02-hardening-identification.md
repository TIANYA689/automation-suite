# 加固与虚拟化的识别

用途：判断一个 APK 用了哪一类保护、以及**测量**它的校验边界落在哪一层。
服务对象是本套件的两条主线：自有代码保护的自测、以及授权样本的分析定位。

**本篇只到识别与度量为止。** 如何让某个校验不再生效、如何绕过完整性判定、
如何规避检测，都不在本套件范围内——需要那类内容时应当先回到需求侧澄清授权边界。

**强度约定**：`[observed]` 有实测样本，`[inferred]` 由机制推出，`[unverified]` 为转述或假设。

## 壳的识别

典型形态：manifest 里的 `application android:name` 被换成一个第三方 stub 类；
启动时壳加载自有的 native 库（常常在首次启动时解出）；从 `assets/` 解密出真 dex；
可选做一轮校验；然后把生命周期转发给真正的 `Application`。

常见壳族名（用于字符串与库名匹配）：jiagu、weapon、leggu、360、ijiami、bangcle。

**一个高价值的拒绝信号**：

```text
UnsatisfiedLinkError: JNI_ERR returned from JNI_OnLoad in "<app>/.jiagu/lib<shell>.so"
```

这是壳**主动拒绝**，含义与另外三种失败完全不同，不要混为一谈：

| 症状 | 真实含义 |
|---|---|
| `JNI_ERR returned from JNI_OnLoad` | 壳主动拒绝（校验未通过） |
| `dlopen failed: library "X" not found` | 你自己引入的依赖缺失 |
| `CANNOT LINK EXECUTABLE` / relocation 相关 | 你的 ELF 本身有问题 |
| `ClassNotFoundException` | 组件被改名后解析不到 |

## 代码虚拟化的三个 tell

症状是"没有壳，但一改就死"。三个特征按可靠性排序：

1. **整个类的方法都是无实现的 `native`**，包括生命周期方法与 getter。
   判据要带比例感：**两个 native 是正常的，六十个就是虚拟化了**。
2. **`<clinit>` 里注册 native 方法**——典型形态是调用一个 loader 类的
   `registerNativesForClass`，或者出现 `special_clinit_*` 这类合成名。
3. **SONAME 与文件名不符**——读 `.dynamic` 里的 `DT_SONAME`，
   例如文件名是 `libx.so`，而它自称 `liblinkerloader.so`。

支持性线索：`assets/` 下有小体积文本描述符（含保护器名与版本）；
native 库被织进其他库的 `DT_NEEDED` 链；loader 自己会打带 tag 的日志。

## 运行时识别

| 运行时 | 特征文件 |
|---|---|
| Flutter | `libflutter.so` + `libapp.so` + `assets/flutter_assets/` |
| React Native | `libhermes.so` 或 `libjsc.so` + `index.android.bundle` |
| Unity | `libunity.so` / `libil2cpp.so` + `assets/bin/Data/` + `globalgamemanagers` |
| Cordova / Ionic | `assets/www/` + `cordova.js` |
| Xamarin | `libmonodroid.so` + `assemblies/` |

一条通用启发：**如果 `classes.dex` 相对于整包体积小得不成比例，真代码就在别处。**

## 按 stub 比例给 dump 形状分类

用"方法体被清空的比例"给样本形状归类，这是可复现的度量而不是印象：

| 形状 | 特征 |
|---|---|
| 真身 | 比例接近基线（未加固） |
| 抽取壳骨架 | 比例高 |
| JNI sinking | 整类 native，**且**有 `Java_*` 导出符号 |
| Java2C | 薄转发器 |
| 动态注册型 sink | 整类 native，**且没有** `Java_*` 导出 |
| 真 dex 虚拟化 | 有方法体，但反汇编出来是乱码 |

## 单变量度量校验边界

要回答"这个保护的校验边界在哪一层"，唯一可靠的办法是**一次只改一个变量**，
每次改动走一遍完整的安装与启动：

1. **基线**：不改任何东西，只重签名。**这一步失败就停**——那是你的流水线或环境的问题，
   不是目标的问题。
2. 对已存在文件做**语义惰性**的改动（例如翻转一个注释段的一个字节）。
3. 新增一个良性 ELF。
4. manifest 组件**等长重命名**（选一个惰性 activity）。
5. 结构性改动（移动 program header、加 segment、加 relocation）。

**边界通常是不均匀的**：常见结果是"已有库可以改，新增库不行"、
"activity 可以改，provider 不行"。所以不能用一个结论概括整层。

一个必须知道的机制：**provider 在进程启动时由系统实例化**，
所以改名会在 `Application.onCreate` 里就失败并杀死进程；
而 activity / service 是惰性解析的，代价低、风险小。
等长改名能保持二进制 XML 的 chunk 结构有效，不需要重编码。

## 宿主三条件

要判断某个 native 库能不能作为分析落点（也是自测保护强度时的三问）：

1. **它真的被加载了吗**——查进程的映射，而不是查包内有没有这个文件。
   包内有但没映射，说明是惰性 SDK。
2. **它可改吗**——见上面的边界度量。
3. **其中有没有东西足够早被调用**——导出 `JNI_OnLoad` 是最理想的，
   因为它由运行时自动调用。

## 完整性校验的证据来源

一个加固器能读到的"证据"就这几类，识别时逐条对：

- APK 签名
- `AndroidManifest.xml`
- 壳自己的 native 库
- 壳自己加载出来的 dex
- 环境信号（提权、模拟器、插桩、调试器）

**关键认识：你自己的重签名本身就是一次被检测的改动。** 所以"改完就死"未必是逻辑错了。

## 检测挂在哪一层

要判断某个校验是在 Java 层还是原生层/运行时层：

- 在 Java 层挂钩相关 UI 组件并打印调用栈。**如果挂钩该组件类零命中**，
  说明界面是运行时或原生层画出来的，校验大概率也在那一侧。
- **最便宜且最高价值的对照**：拿官方未改动的构建与重打包构建，
  用**同一个探针**跑一遍做差异对照。

## 度量方法体清空比例

**定义**：在有 `code_item`（`code_off != 0`）的方法里，指令流（跳过纯 nop）
只剩下单个 `return*` 的比例。`code_off == 0` 是 abstract / native 声明，正常，要排除。

在一份约 982KB、5061 个方法体的 dex 上的校准结果 `[observed]`：

| 形态 | 比例 |
|---|---|
| 未加固对照 | **1.9%** |
| 裸 `return-void` | **100.0%** |
| `const/4 v0,#0; return v0` | **93.2%** |
| nop 填充、无 return（清槽） | **0.0%**——**盲**，低于未加固原版 |
| `new RuntimeException; throw` 型 stub | **1.9%**——**盲**，与对照无法区分 |
| 清空 25% / 50% / 75% | **1.7% / 1.7% / 2.1%** |

三个必须记住的推论：

- **分布是双峰的**：要么接近基线，要么接近 100%，中间没有过渡带。
  **因此没有阈值可设，部分抽取是不可见的。**
- **比例高是决定性的，比例低什么都不是。**
- **排序会失效**：实测出现过"清空 25% 的样本排到未加固对照前面"（1.7% vs 1.9%）。
  所以这个指标只能用于**高比例的确认**，不能用于低比例的排除。

**去重按内容哈希，从不按文件大小。** 实测同样大小的两份 dump 有约 **73%** 的字节不同。

## 三道递增成本的检查

按代价从低到高，前一道不过就不要做后一道：

1. 两条独立读路径拿到的同一段字节，哈希一致。
2. 一个**你没有写**的生产者能解析它（用成熟反汇编器，看它自己的失败计数）。
3. 才轮到解释那些比例数字。

第 2 条是分界线：判定"这是不是真的字节码虚拟化"必须用**你没写过的解码器**。
实测案例：手写表报出两万多个不可解码单元，而平台解码器返回数十万行、
数万个指令解码、零结构错误——一直是普通 dalvik `[observed]`。

## 静态读数能许可什么

静态探测能回答：

- 方法体是不是真的 dalvik 字节码（**能**）
- 代码是不是离开了 dex 去了原生层（**能**）

静态探测**不能**回答：

- 原生岛是否在校验签名 / 提权 / 调试器（**不能**）
- `assets/` 下未标注的 blob 是不是活的（**不能**）

**所以一份干净的静态读数只许可"这不是 dex 虚拟化"，不许可"这没有加固"。**
把后者写进结论，就是典型的能力越界。

## 诚实的停止点

- **基线对照失败就停**，先修流水线。
- 目标是**真**虚拟化时，直说"到这里为止"：上游自己的立场是它**不会**把这类样本交还给你反编译，
  恢复成本通常是**数周而不是一个下午**，而且每个厂商每个版本都要重做；
  相关步骤在源头文档里也只是**研究计划**而非配方。
- 同一个变量**两次相同失败就是停止信号**，不是去试第三个参数。
- 静态 dex 指标**看不见只在运行时存在的加固**：实测一个虚拟化样本在静态上看
  两万多个方法里只有 7 个 native、stub 比例 4%，毫不起眼 `[observed]`。
