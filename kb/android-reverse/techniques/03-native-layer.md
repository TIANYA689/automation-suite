# 原生层结构与 JNI 约定

用途：涉及 `.so` 的加载行为、符号查找、JNI 边界与指令级追踪时读这一篇。
它装的是 **ELF / 链接器 / JNI 的工程事实**，以及各类分析手段**实测到的边界**。

**不覆盖**：运行期替换 Java 方法实现、中和自毁路径、绕过完整性校验——
这些属于"降低安全机制"，不在本套件范围内。

**强度约定**：`[observed]` 有实测，`[inferred]` 由机制推出，`[unverified]` 为转述或假设。

## 为什么原生层值得单独看

三个理由，都在"Java 层看不到"这个方向上：

- 它的初始化**早于任何应用代码**。
- 它持有跨 Java 状态重载 / 重初始化仍然存活的状态。
- 当字节码侧被完整性校验覆盖时，原生侧常常不在同一套覆盖里。

## auto-load 陷阱：mapped ≠ initialised

最容易踩的一条：

**`DT_NEEDED` 会让链接器把第二个库映射进来，但不会调用它的 `JNI_OnLoad`。**
纯动态链接器加载的结果是"已映射、未初始化"。

推论：如果某个逻辑依赖 `DT_NEEDED` 拉起的库，它的入口必须是
**ELF constructor 或 `DT_INIT`**，不能指望 `JNI_OnLoad`。

而 constructor 跑得**极早**，此时运行时可能还不存在。所以 constructor 里的逻辑要允许
"太早失败、稍后重试"，且**首次失败不能是致命的**。

## relocation 与页权限

两条会决定"某些改动根本不可行"的约束：

- 目标在 load 时**必须是可写的**，否则会在重定位实现里触发访问权限错误。
  现代 Android **拒绝同时可写与可执行的页**。
- **相对重定位无法修复位于"仅可执行"页上的指针槽**。

## 架构事实的唯一 ground truth 是活进程的映射

属性查询（`getprop`、`primaryCpuAbi` 一类）给的是**预测**，不是事实。
唯一可靠的做法是看**活进程的实际映射**。

两个必须知道的干扰项：

- **翻译层会改变时序、校验结果与挂钩行为**（如各类 ARM-on-x86 翻译层、`native_bridge`）。
  **在翻译层下通过的结论，不是硬件上的结论。**
- **fat APK 在安装时只解出一个 ABI** 进安装目录。所以"包里有哪些 ABI"和
  "设备上跑的是哪个 ABI"是两个问题。

## JNI 的三种形态

| 形态 | 符号表表现 | 分析含义 |
|---|---|---|
| 静态链接 | `.dynsym` 里有 `Java_<包>_<类>_<方法>`（经混淆工具会变形） | 可直接按名查找 |
| 动态注册 | 符号表**可能是空的**，靠 `RegisterNatives` 注册 | **按符号搜索会静默失败** |
| native → Java 回调 | 用 `FindClass` / `GetMethodID` / `CallObjectMethod` | 需要看调用序列 |

**动态注册让符号搜索静默失败，有两个独立机制：**

1. 动态注册本身就不产生 `Java_*` 导出。
2. **`-fvisibility=hidden`** 编译选项；以及 C++ 的 `jni.h` 把 `RegisterNatives` 实现为
   内联成员（走函数表），**因此根本不产生符号**。

实测：一个真实使用动态注册的库，符号表里含**零个** `RegisterNatives` 符号 `[observed]`。

**有效检查**：**导出了 JNI 入口、同时导出零个 `Java_*` 符号 ⇒ 就是动态注册。**

## Java2C 与 JNI sinking 的判别

判别量是 **native 声明密度**（native 方法数 / 总方法数），两者的分离度约**三个数量级**：

| 样本 | 密度 |
|---|---|
| JNI sinking 样本 A | **0.04%** |
| JNI sinking 样本 B | **0.03%** |
| 带真 JNI 库的应用 | **0.03%** |
| Java2C 形状夹具 | **82.76%** |

**构造函数要排除**：翻译实践会把 `<init>` / `<clinit>` 留在 Java 侧，
所以"每个方法都是 native"是不可达的，别拿它当判据。

强判据（实测）：

- `Java_*` 符号数与字节码里的 native 方法数约 **1:1**（实测 2:2、3:3）。
- 每个 Java 方法对应一个 C 函数，开头是 `JNIEnv *env, jobject thiz, …` 形态。
- 出现工具链特征串（转换器名、`dynamic_register_compile_methods`、
  `ScopedLocalRef`、`well_known_classes`）。

弱判据（只能作辅助）：`JNI_OnLoad` 存在、出现 `RegisterNatives` 字符串、
链接了 C++ 运行库、每类平均字节数（**未标定**，夹具与真实目标的数值区间不重叠）。

**JNI 边界上的符号搜索会静默失败**——见上一节的两个机制。这是最容易把
"没搜到"错读成"不存在"的地方。

## 指令级追踪与去混淆

混淆变换按"哪个让静态读失败"来识别：

| 变换 | 识别特征 |
|---|---|
| 控制流平坦化 | 静态上单支配块 + 状态变量常量 + switch / 跳转表；动态上调度块在直方图里大幅领先，序列呈 `调度 真实块 调度 真实块 …` |
| 虚假控制流（不透明谓词） | 垃圾分支在 trace 中**从不出现**——只有当你构造的输入**会**走到它时，它出现才算证据 |
| 指令替换 | 结果正确；**单看 trace 无法简化算术**，需要符号执行或暴力扫描 |

工具选择：块级 trace + 计数；调用边；导入函数（走 relocation 而不是 trace）；
崩溃定位；状态约束（符号执行）；单指令定值（确定性插桩）；无设备时用仿真器。

**追踪的三条纪律**：

1. 只跟**一个**触发点。
2. 过滤到**一个**模块。
3. 给块数**设上限**。

一个实测陷阱：取"主线程 id"的接口在实践上**不返回** Android 主线程
（实测跟随的线程 id 与进程 id 不同，结果零事件；Android 上主线程的 tid 等于 pid）。

**实测三臂**（同一设备、同一包、同一模块，各跟随 6 秒）`[observed]`：

| 臂 | 结果 |
|---|---|
| 附着 + 恢复，不跟随 | 存活 |
| 跟随，不排除任何模块 | **进程死亡**，脚本被销毁 |
| 跟随，排除 20 个系统模块 | 存活，但 `blocks=0 blk=0 calls=0` |

**结论**：排除模块能保命（`[observed]`），但**排除并不能恢复事件投递**。
把"零事件"当成"目标什么都没做"是错的。

**几条实测边界**：

- 零事件在特定组合下可复现（原因 `[unverified]`）。
- **trace 只证明被跟随线程在窗口内执行了什么，不证明 absence**；
  计数只有在 `truncated=0` 时才算证据。
- 高频跟随 / 取消跟随会让系统进程在数百个周期后崩溃（`[observed]`），
  栈顶落在动态二进制插桩的代码缓存里。
- 成本：一次跟随进入系统库会把 8 核机器负载推到 34 以上，**毁掉另一个并发任务**。
  所以不要在还有独立工作在用同一台设备时开追踪。

## Dart AOT / Flutter 分析

**第一步是 pin 版本**，因为快照格式随版本变化。但注意 banner 会撒谎：
实测一个 banner 报 `0.0.1`，构建 id 字段为空，既没有 `(stable)` 也没有时间戳。
**判别法**：找架构后缀、从前面取 NUL 结尾的串、确认 `(stable) (…)` 尾部存在；
**缺了就直说不能 pin**，不要为那个 `0.0.1` 去建反编译器。

两条路线：

- **纯静态前端**（Go 单二进制，无虚拟机、无需 SDK 编译）。实测在一份 Dart 3.6.0 的
  `libapp.so` 上给出三万余个函数、六千余个类布局、三万余个池条目、十七万余条调用边，
  95.7% 的间接调用点带注释 `[observed]`。
  **注意它的 `doctor` 报的版本是结构 profile 标签，不是 SDK 版本**
  （实测打印的版本与 banner、快照哈希、字节搜索三者都不一致）。
- **需要自行构建的前端**（嵌入匹配的 Dart 虚拟机，产出规范化清单）。
  它是要你构建的源码树，不发布预编译产物；需要构建工具链；实测全流程约 **78 秒**。
  新构建的二进制若立即无输出地崩溃，**不要对样本下结论**，重新链接再试。

**两个偏移空间不同，且没有换算常数**：池偏移与文件偏移之间的映射是"重建出来的池"的属性，
不是文件的属性，**无法从 `libapp.so` 单独算出**。实测同时出现在两处的 4241 个字符串，
产生了 **4237 个不同的差值** `[observed]`。所以不要描述成"本流程能自己解码对象池"。

寄存器与字符串编码（Dart 3.x / arm64）：池基址、当前线程、堆基址、
null 与布尔基址、Dart 栈指针、类分派表各有固定寄存器；
布尔常量用基址加固定偏移表达。字符串 tag 编码为
`0x80 | (长度 << 1) | 双字节标志`，单字节是 ASCII / Latin-1，双字节是 UTF-16LE。
**必须按链式结构验证**，否则会得到大量错位噪声——实测逐字节扫数 MB 快照得到约
88 万个"字符串"，几乎全是假的 `[observed]`。

**32 位 ABI 的格式结论被推翻（实测）**：armv7 快照里**不存在**上述打包 tag 方案，
字符串表不是可遍历的链。抽取器在该 ABI 上报"保留 0 条"是**格式不匹配，不是空表**
（同一应用 arm64 快照保留 4980 条链式条目）。
同应用双 ABI 实测显示：**armv7 的字面量内联在只读数据里，是 UTF-8 而不是 UTF-16**，
普通字节搜索即可。

**不分发的依赖**：Dart AOT 分析需要一个**快照解析前端**，本套件不提供也无法合成；
池与文件偏移的换算就是它给的。**在流程开始前说清楚用的是哪一种**，
因为不同前端对同一个二进制会报出不同的 Dart 版本标签。

## 诚实的停止点

- 要分析的库**不在活进程的映射里** ⇒ 停，先选对库。
- 追踪零事件的结论**很窄**，不要扩大；`exclude` 不是零事件的解药。
- 只对一个 ABI 做的改动是**受控实验，不是交付物**。
- 版本无法 pin 就说无法 pin，不要为错误的版本号建工具链。
