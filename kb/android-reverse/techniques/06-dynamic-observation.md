# 动态观测与仿真调用

用途：需要在运行时观测行为、或需要在无设备条件下调用目标函数时读这一篇。
它装的是**观测纪律、观测能力的边界、仿真与真机的分工、以及工具对齐门槛**。

**不覆盖**：让目标检测不到插桩、对抗反分析、绕过环境自检。这类内容不在本套件范围内。

**强度约定**：`observed` 有实测，`inferred` 由机制推出，`unverified` 为转述或假设。

## 附着还是启动注入

- **时序敏感的场景必须用启动注入。** 附着会错过初始化、首批网络请求、闪屏阶段——
  而这些恰恰是最常需要观测的部分。
- **ABI 必须与设备实际执行的一致**，不是与包里声明的一致。
- **恢复执行前必须等脚本的就绪信号。** 提前恢复会丢掉最开始的一两百毫秒，
  而那一段正是初始化所在。

## 零事件的排查顺序

零事件最常见的误读是"目标没做这件事"。按这个顺序排除，顺序本身就是排查路径：

1. **目标类 / 方法 / 重载不存在**——混淆名、内部类改名、参数类型与预期不符
   （例如实际是对象类型而你按字符串类型挂钩）。此时包装器从不被调用。
2. **类加载器不对**——多 dex、插件化、加固目标会有多个加载器；
   默认用的是应用加载器，于是报找不到类。**要枚举加载器再切换。**
3. **路径没走到**——在更早的失败点加观测，看它究竟断在哪里。
4. **界面动作没有触发业务逻辑**。
5. **运行时没有语言桥**——此时绑定是"未定义"，与"没找到"是两回事。
6. **附着到了错误的进程**——多设备场景下每次都要显式指定设备号。

**三条观测纪律**：

- 只跟**一个**触发点。
- 过滤到**一个**模块。
- 给输出设**硬上限并去重**。极热路径上的输出（例如异常消息）必须设上限，实测取 400 条。

## 进程存活与事件投递是两件事

- 从 shell 起的服务会随 shell 退出被回收，挂钩在约一分钟后停止。
  要用脱离会话的方式启动，并且**每次实验前确认进程还在**。
- **让进程存活不等于恢复事件投递。** 实测：排除若干系统模块后进程存活，
  但块数与调用数**仍然是 0**。
- 启动注入期间部分界面起不来（焦点为空、截图为空）——那是"还没渲染"，不是"坏了"。
  正确顺序是：启动注入 → 附着 → 内存改写 → **脱离** → 正常启动。
  **不要在附着状态下用一张空白截图得出"没有界面"。**

## 观测能证明什么，不能证明什么

**能证明**：

- 某方法在**本次运行**被调用的真实调用链。
- 某个域名从未被解析 ⇒ 该子系统从未启动。这比"日志很安静"强得多，
  因为日志安静也可能只是它从不打印。

**不能证明**：**未观测 ≠ 未发生。** 挂钩没触发，可能只是挂错了位置。

**计数要成为证据，前提是先证明挂钩能在该目标上触发。**
在证明这一点之前，"没有挂钩触发"不是事实。

## 把目标服务化

机制：脚本导出若干函数后即可从外部调用，参数与返回值需可序列化。

**验收判据**：至少一次调用的输入 / 输出要与**独立来源**核对
（设备日志、服务端响应、或已知答案）。

**"脚本加载成功"不算成功**——加载只证明注入成功。
加固目标会出现"加载成功、之后每次调用都报脚本已销毁"这种形态。

实测失败模式，遇到时不要当成目标的性质：

| 现象 | 真实原因 |
|---|---|
| 注入后进程被杀 | 加固目标会杀掉注入 |
| 用着用着断连 | 系统回收了服务进程 |
| 按名字附着失败、按进程号成功 | 名字解析路径不可靠 |
| 连不上默认端口 | 服务改听了非默认端口 |
| 附着超时 | 目标进程繁忙 |
| 刚连上就断 | 目标进程短命，几秒就退出 |

## 仿真调用：什么时候用

**适用**：代码在加固库内静态不可读（控制流平坦化、字符串加密、虚拟化），
而你要的是**输出**（签名、解密结果、令牌），并且需要大量调用。

| | 仿真 | 服务化调用 |
|---|---|---|
| 环境 | 自建，是假的 | 真实 |
| 设备 | 不需要 | 需要 |
| 对反注入 | 有效 | **无效**（注入本身就是门票） |
| 吞吐 | 批量千次 / 分 | 几十次 / 秒 |
| 起步成本 | 高 | 分钟级 |
| 每缺一个系统调用 | 就要新加一个桩 | 不存在这个问题 |

**两者皆可时优先服务化调用**——设备已经把真实环境给你了。

**两击规则**：仿真方向两轮定向打桩仍跑不起来就换路线，**不要试第三轮**。

**环境桩分级**（决定该不该走这条路）：

- **纯上下文查询**（包名、文件目录、包管理器）→ 打桩即可。
- **跨进程调用**（Binder、SDK）→ 桩面爆炸，改走服务化。
- **硬件校验**（密钥库、可信执行环境、远程证明）→ 大概率死路。

**调用约定**：位数必须与**目标库**一致，不是与主机一致；
先跑初始化入口（它会解密、注册 native 方法），再调目标方法。

**仿真结论的迁移程度**：必须与真机**对拍**（同输入比输出）。
不一致反而比读库更快定位缺了哪个部件。

- **可迁移**：调用约定、批量样本。
- **不能得出**：依赖真机环境的值（时间、随机数、文件、其他库的状态）；
  "算法在设备上也是这样"；任何硬件相关结果。

## 工具版本对齐是硬门槛

| 症状 | 原因 |
|---|---|
| 找不到 Android 动态链接器 | 工具过新，退到仍支持该系统的版本 |
| 语言绑定未定义 | 新版移除了内置语言桥 |
| 连接失败 / 消息无效 | 两端版本不一致 |
| 实例枚举直接抛错 | 运行时未就绪 |

多设备场景下**不要依赖自动选择**，每次显式指定。

**需要自行构建的工具**：留意构建产物的架构与主机工具链的位数；
构建目录与缓存路径在非交互环境下可能不可见。

实测成本（原样）：一个 Rust 重写工具在干净检出上构建约 **117 秒**，产物 2.13 MB；
一个 Java 仿真框架在 Windows + JDK 17 上构建约 **48 秒**，
但它**没有仿真过任何真实目标库**——所以它那些"每个库需要哪些桩"的声明**全部是 `inferred`**。

**这条本身就是一条纪律**：工具构建成功不等于路线被验证过。

## 诚实停止点

- 附着不可用时，**不要在同一轴上继续升级**；加固目标杀掉注入时不要重试同一种附着，换路线。
- 两轮打桩不跑就停。
- 目标若自校验解密密钥、或拒绝非启动环境，**不值得仿真**——这是结论，不是失败。
- 要观测的库不在活进程映射里 ⇒ 停，先选对库。
- **一次**复现、记录、改走静态——**不要花整个会话去证明某条路不可能**。
