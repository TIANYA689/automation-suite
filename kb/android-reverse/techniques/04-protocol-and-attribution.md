# 协议逆向与门禁归属判定

用途：抓到的流量解不开、或要判断"这个限制到底是客户端还是服务端说了算"时读这一篇。

**核心立场**：本套件吸收的是**判定**——判断一个门禁归谁所有、一个失败出在哪一层。
**不吸收打破服务端授权的方式**，也不吸收让客户端校验不再生效的做法。
判定做对了，结论常常是"这个改不动"，而这本身就是一个可交付的结果。

**强度约定**：`[observed]` 有实测，`[inferred]` 由机制推出，`[unverified]` 为转述或假设。

## 无 schema 的 protobuf 解码

格式要点：varint 用 base-128、低位组在前；`tag = (字段号 << 3) | 传输类型`；
传输类型 0 = varint、1 = 定长 8 字节、2 = 长度前缀（字符串 / 字节 / 嵌套 / packed）、
5 = 定长 4 字节；类型 3 / 4（group）视为不支持。

**三个必然的后果，决定了能下什么结论：**

1. **字段号只属于它所在的那条消息**。同一个字段号在嵌套层里含义不同，不要跨层归并。
2. **packed 编码在无 schema 时只能报"不透明字节"**，元素边界未知。
3. **解码出 0 不等于字段被赋值**——proto3 的隐式默认值不上线，所以"0"和"没这个字段"不可区分。

工具：官方的 `--decode_raw` 最省事；第三方 inspector 类工具可用性 `[unverified]`；
需要可控输出时用自研解码器（支持分帧、最大深度、重编码）。

**最强证据是往返一致**：解码 → 重新编码 → 与原字节逐字节相同。
实测在内置夹具上 26/26、对官方运行时 21/21、分帧检查 8/8，
并且一个真实容器字节精确往返 `[observed]`。
**注意候选表里的置信度数值是排序，不是概率。**

往返一致**不能**推出：字段类型、packed 边界、缺省是否等于 0、字段号归属，
也不能推出"能解析 ⇒ 这是真消息"。

恢复 schema 的两条路线：从字节码里读解析逻辑的 `case → read*` 建表，
再用带 schema 的解码器逐样本验证（`[inferred]`）；
或读某代运行时内部的描述结构（版本敏感，`[unverified]`）。

## gRPC

识别：方法为 POST、`content-type` 为 gRPC 系、路径形如 `/包.服务/方法`。

帧结构：**1 字节压缩标志 + 4 字节大端长度 + 消息体**，按长度重组。
**结果在 trailers 里**（状态码与状态消息），所以"HTTP 200 且无响应体但状态非零"
是一个**正常的错误**，不是异常。

重组后交给无 schema 解码器即可。

**一个会造成严重误判的限制**：只懂 HTTP/1.1 的代理**只看到隧道，看不到帧**，
于是会被读成"这个应用没有发请求"。

## QUIC / HTTP3 的限制

症状很典型：代理正常、证书正常、**抓包为空**（UDP + TLS1.3，没有 CONNECT，
也没有可终止的 TLS 层）。

识别：响应头里的 `Alt-Svc` 宣告 h3、出现 UDP 443、ALPN 协商为 h3。

缓解顺序（从便宜到贵）：先封锁 UDP 443 把它逼回 TCP——但这属于**改变了网络条件**，
必须写进报告；其次是导出 TLS 密钥日志的方式（浏览器系支持，Java 系一般不支持）；
最后才是改客户端关掉 h3（属于重打包决策）。

**这一节全部是 `[inferred]` / `[unverified]`，本套件没有实测过。**

## 证书固定：只做归因

三类固定，分析含义完全不同：

1. **客户端库级固定**（如某个 HTTP 客户端的 pinner、自定义信任管理器）——
   作用在客户端进程内，系统级模块对它无效。
2. **系统信任决策**——标准链路。
3. **应用自带库验证**——例如 Flutter 自带的 TLS 实现、或捆绑的 C 库。
   这类只有改**那个库自己的验证路径**才有效，系统层拦截不生效。

**归因价值在于**：一个只影响某功能的网络错误，**先判是不是服务端证书本身的问题**，
再怀疑改动。上游把"没查服务端证书就当成改动问题"列为反模式。

定位自带库验证路径的做法（`[unverified]` 转述）：从字符串锚点出发找交叉引用、
按函数参数个数筛选（**3 个参数**的那个通常就是证书链校验入口）、得出相对虚拟地址。
两个必须记住的核验要求：

- **字符串锚点是构建产物**，丢了就要退到结构化搜索（调用链），成本更高。
- **锚点找错是静默成功的**——你挂钩了一个无关函数，看起来一切正常。

**通则**：任何"看起来生效了"的观察，都必须在**本会失败的那条路径**上确认，
否则无法与"根本没触发"区分。这与验证阶梯里"用三个独立信号"是同一条纪律。

## 门禁归属判定（本篇最重要的产物）

判定顺序：先定服务端权威，再动客户端。

**抓 API 面**：基础地址、路径、认证头、动态网关（硬编码的地址可能只是兜底）。
复现时用真实请求头（**一个自定义头常常决定网关是否放行**）、正确的 UA，
并注意 CDN / WAF 的干扰（403 加一个 HTML 页 = 请求形状不对）、
自己的出口地域、以及健康检查端点（信息密度极高）。

**归属矩阵**：

| 探测 | 客户端拥有 | 服务端拥有 |
|---|---|---|
| 受保护端点，不带凭证 | 仍然成功 | **401 / 403** |
| 伪造 token | 仍然成功 | **401 / 403** |
| 元数据端点 | 返回完整 | 返回 200 但**省略**受保护字段 |
| 列表 / 配置端点 | 返回 200 带数据 | 返回 200 带数据 |

**判据**：值在 200 响应里**缺失** ⇒ 客户端改不动，如实记录。

改参数之前先探非法值：返回 400 加校验信息说明是白名单（顺带能拿到全部合法值）；
返回 404 说明路径是精确匹配的。

**本套件只判"谁拥有门禁"，不教打破它。** 结论落在证据表里时，
"打破服务端权威"应当被列为**范围外**，而不是硬打。

## 差分验证闭环（可迁移的方法论）

这套做法解决一个通用问题：**已知一个变换存在，如何在不看它的前提下反推出它的映射。**
它的价值不在 Android，在于它的验证结构。

**三个前提**（任一不成立就直接放弃这条路，不要硬撑）：

- 变换后的体积**不变**（变了就判 `resized` 拒绝）。
- 变换是**按指令**而不是按方法替换的（否则目标方法变成 stub，判 `NOT-USABLE`）。
- 方法体**仍在字节码里**（否则判 `stripped`——这是最常见的死因）。

**覆盖夹具**：用编译器与转换器生成覆盖尽量全的指令集合。
实测在 224 个 opcode 中达到 **218（97.3%）**，
剩下 6 个是**结构上不可达**的（需要超长常量池、触及方法体积上限、
没有语言字面量、需要两个大于 256 的寄存器、或转换器根本不产出该编码）`[observed]`。
**每次都要报覆盖率**，因为覆盖率决定了这张表的适用范围。

**闭环验证**：用已知的双射重标 → 再比对 → 精确重导。
实测 **218 行、218/218 恢复、零错误、零捏造、零非单射、可用** `[observed]`。

**注入性检验（这一步最容易被跳过）**：在 stub 场景下正向读会显示"完美"（218 条全部高置信）。
**只有反向检查**——一个字节被多少个原始 opcode 认领——才会暴露问题。
这就是"正向通过不等于结论成立"的实例。

**成本判定**：流程的六个环节里，**有一个环节完全无法自动化**
（向第三方平台提交硬化请求：无公开接口、有限流、需注册审核、产物常只是一个下载页、
耗时从分钟到天、合成夹具还可能被拒）。

**因此不要造全自动流水线。** 正确做法是：确定性的环节做本地工具，
需要判断的环节做"清单 + 一个脚本"，人工环节**记录在案**；
最终交付物是**一份带边界的报告，而不是一条流水线**。

**退避阶梯**（越往下越保守）：`stripped` / `resized` / 共享字节 ⇒ 停；
部分可用（冲突 ≤30%）⇒ 只用高置信行并声明；
覆盖率低 ⇒ 表全但 opcode 集合不全。

**最高一级退避，也是最常被忽略的一条**：先问所需的行为是不是**根本不在**被保护的那个岛里
——如果它在边界之外，一小时的方案远胜数周的表恢复。
