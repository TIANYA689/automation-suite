# APK 容器与 dex 字节码结构

用途：涉及 APK 容器的解析、重建、签名与改动审计时读这一篇。它只装**结构事实与校验手段**，
不装"改什么能达成什么目的"——那属于需求侧，不属于知识侧。

**强度约定**：本篇结论凡带 `[observed]` 的，来源是一次真实样本上的执行；
带 `[inferred]` 的由机制推出；未标注的按 `[inferred]` 处理。

## 容器层：什么会让包加载失败

APK 就是一个 zip，但有几条硬约束，违反了不会在打包时报错，只在安装或启动时报错：

- `AndroidManifest.xml` 与 `resources.arsc` 必须 **STORED**（不压缩）。压缩了照样能生成，
  装的时候才拒。
- targetSdk 30+（Android 11+）要求 `resources.arsc` 的数据偏移 4 字节对齐，
  否则报 `... aligned on a 4-byte boundary` 一类的失败码。未压缩的 `lib/` 下的 `.so` 同规。
- **zip extra 区最小 4 字节**。需要补 1–3 字节才能对齐时，这个空间**在 extra 区里无法表达**，
  必须插入等长的 STORED 填充项。这是"差一点点对齐"最容易被忽略的一条。
- `extractNativeLibs=false` 时，`.so` 从包内 mmap，因此必须未压缩且页对齐。
  对齐做错的症状很迷惑：**装成功，启动时死在 linker**。

## dex 头：校验和的写入顺序

dex 头里两个校验字段有**先后依赖**：

```text
1. 先算 data[32:] 的 SHA-1，写进偏移 12..32
2. 再算 data[12:] 的 adler32，写进偏移 8..12（这一步覆盖上一步写进去的签名）
```

顺序反了，头看起来完全合理，但**永远通不过校验**。失败症状尤其危险：
系统记下 `Bad checksum (computed, expected)`（真实值在 `expected` 一侧，要从结果反读），
然后**回退到解释执行**，于是你看到的是一个跟校验毫无关系的 `ClassNotFoundException`。

还有一个自洽陷阱：部分 R8 产出的 dex 里 `signature` 字段全为 0，
所以在**第一次改动之前**，错序的实现看起来是对的——它只是还没被触发过。

常用头偏移：`file_size` 0x20、`map_off` 0x34、`string_ids` 0x38/0x3C、
`class_defs` 0x60/0x64、`data` 0x68/0x6C。

## 验证器的硬规则

字节码里最容易被静态工具漏掉的一条：**`move-result*` 必须紧邻它的生产者**（`invoke-*`）。
如果一条条件分支能直接落到 `move-result` 上，验证器报 `VerifyError ... type=Undefined`，
整个类加载失败。

注意"前一条是生产者"这种线性检查**看不见分支跳进来**这种形态。所以审计必须走 CFG，
不能走线性扫描。

## 结构校验手段，以及每一件的盲区

盲区比能力更重要——决定你什么时候**不能**宣布"结构完好"。

| 检查 | 看得见 | **看不见** |
|---|---|---|
| 类表差异（比对 class_defs 的名字与 access_flags，重点是 `ACC_INTERFACE`） | 类集合变化、接口性漂移 | **方法体损坏**。表全净，仍可能运行时抛类型变更错误 |
| 验证器合法性检查（CFG 级查"条件分支目标 = move-result"） | 这一类违规 | 只管这一类。其余验证器规则不在覆盖内 |
| 指令定位工具（按解码语义给出精确偏移与分支两侧） | 你要找的那条指令 | 解码对不齐的位置直接跳过 |
| smali 汇编往返 | 汇编是否成功 | **不判合法性**。可以静默产出空 dex 仍然返回成功 |
| 打包工具的包信息检查 | 包名、split 名、`isSplitRequired` 等字段 | **不解元素树**、不判资源语义 |

**结论**：结构校验通过是**必要而非充分**。任何一处代码项损坏都能穿过上面全部检查。

## 改动审计：等长替换是主要盲区

这是最容易造成"以为只改了一处"的地方。

- **等长替换会同时骗过长度审计和字节计数**。实测：长度审计报出 20 个被改动的方法，
  而实际被碰到的有 **24** 个——缺的 4 个全是等长替换 `[observed]`。
- 因此审计要**分两级**：
  - Tier 1：按结构长度变化找差异（误报接近零，但漏等长替换）。
  - Tier 2：对**改动声明里点名的每一个目标方法**逐指令比对。
- **Tier 2 的输入不能取自 Tier 1 的输出**——否则等长替换永远进不了 Tier 2。
  推论：**每一次改动都必须声明它的目标方法签名**，这是流程要求，不是可选项。
- 更稳的 Tier 2 形态是比"某个指令类别的偏移集合"（例如把全部 `move-result` 的偏移列出来），
  这样同时证明了两件事：打中了目标，且同形态的其他位置没被动过。

**字节级 diff 的假阳性**：一次全树往返会重建字符串池并去重，
实测约 **800** 个方法报出差异，其中 **84%** 只差 1–4 字节，全部是索引位移 `[observed]`。
看到"几百个方法变了"先别慌，先看差多少字节。

**合法性检查的四个层次**（从便宜到贵）：汇编是否成功 → 类表差异 → `move-result` 前驱合法性
→ 设备上首次执行。中间那一层要用**集合差**：新增的非法位置必须为 0；
绝对数量没有意义，会被 payload 里的伪指令污染。

**收尾判据**：`缺失集合 = 预期集合 − (Tier1 ∪ Tier2)` 必须为空。
并且**验产物，不验工具的成功信息**——工具的 exit 0 什么也不证明。

## 重打包与签名

- 只删签名件：`META-INF/` 下的 `*.SF` / `*.RSA` / `*.DSA` / `*.EC` 与顶层的 `MANIFEST.MF`。
  **绝不删整个 `META-INF/`**——里面还有 `services/` 这类运行时注册信息，删了功能会静默缺失。
- 重建 zip 时要保留每项的 `compress_type`、`external_attr`、`date_time`。
- 资源重编码（解包工具不带 `-s` 参数时）会把混淆的短名展开，
  产出**上千对"删除 + 新增"**。那不是损坏，是纯重命名。
  **只改字节码时就只换 `classes*.dex`**，不要碰资源。
- 用 `jarsigner` 重写 zip 会破坏对齐，导致安装被拒。用按 v1 + v2 + v3 全签的工具。
- 签名校验工具会**按 APK 自身的 minSdk 选方案**：minSdk ≥ 24 时它报告 v1/v2 不适用是
  **设计如此**，要显式传入 SDK 范围参数才能得到有意义的结论。

**安装失败码是一个家族，不是一条信息。** 同一个 `INSTALL_FAILED_INVALID_APK` 可能是旧签名残留、
base 与 split 不匹配、或对齐问题。**读冒号之后的文本**。同 key 覆盖安装可以保数据；
换 key 必须先卸载，会丢数据。

交付前的清单：签名校验通过 → 装成功 → 启动后进程存活 → 运行日志无致命特征串 →
`META-INF/services/` 下的条目数与原件一致 → **未改动的字节码与原件逐字节一致** →
至少做过一次零改动对照。

## split APK 与 App Bundle 集合

- 集合 = base + 每个 ABI / 密度 / 语言一个 split，**同包名、各自签名**，包管理器视为一个包。
- **可合并的**只有代码与原生成员：`classes*.dex`（需重编号）、`lib/` 下的 `.so`、`assets/`。
- **不可合并的**：任何带 `res/` 或带真 `resources.arsc` 的成员——必须用资源编译器重写表。
  判据很实用：有 `res/` 目录，或表体大于 1KB（占位表只有几十字节）。
- 合并必须清掉 `isSplitRequired="true"`，否则报缺 split。
- **统一重签**：整个集合用同一个 keystore，v1+v2+v3 全签。
  验收判据是**整集只有一个证书**。只签 base 会导致整集被拒。
- 装的时候用多包安装命令；厂商拦截时可能需要提权安装。

**设计上不做的事**（要写进结论，而不是硬做）：不合并资源、不把单体拆回模块、
不做 `.aab` 到 APK 的转换（那是资源打包工具的职责）。

两个命名陷阱：split 名用下划线（如 `config.arm64_v8a`），而 `lib/` 下的目录用连字符
（如 `lib/arm64-v8a/`）。

从设备上拉下来的集合无法用原包名重装（厂商证书），需要先等长重命名包名并重算 dex 头再重签。
成员里的 Java 类**不必**位于 manifest 的包名下——实测几百个类全部在另一个前缀下 `[observed]`，
所以改包名往往不需要改字节码。
