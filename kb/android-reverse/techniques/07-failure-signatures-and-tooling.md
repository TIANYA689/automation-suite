# 失败特征与工具链坑点

用途：出现一个看起来毫无头绪的报错、或怀疑"工具在骗我"时读这一篇。
它装的是**失败特征 → 真实原因**的对照，以及环境、设备、工具、构建四类机械性坑点。

**通则**（判定与归因类）在 `kb/android-reverse/techniques/08-evidence-and-attribution-pitfalls.md`。

**强度约定**：`observed` 有实测，`inferred` 由机制推出，`unverified` 为转述或假设。

## 失败特征 → 真实原因（本域最有用的一张表）

**先读表，再读栈。** 这张表里的每一条都对应一次真实的时间损失。

| 日志 / 报错 | 真实含义 |
|---|---|
| 模块主调度器缺失 | 删掉了整个 `META-INF/`，丢了运行时服务注册 |
| **无关类**的"找不到类" | 同上；或字节码字符串表失序 |
| 找不到 Application 类 | 字符串表失序（等长替换越界到邻居之间） |
| 类型变更错误 / 验证错误 | 全树 smali 往返破坏了编译器生成的合成桥方法 |
| 启动进程失败 + 强制停止，**且无任何 Java 异常** | 同一个文件被二次序列化；也可能是设备本身坏了 |
| 未捕获异常但**没有栈** | 数据结构编码缺外层包装（写数据时的典型症状） |
| 打不开数据库，目录不存在 | 重装后数据目录的属主标识不匹配 |
| 签名校验报告 v1/v2 为假 | 目标 SDK 较高时工具按自身规则决定查不查，**不是真失败** |
| 找不到 Android 动态链接器 / 语言绑定未定义 | 插桩工具两端版本不匹配 |
| 证书链校验失败 | 服务端证书过期或链不完整，**与你的改动无关** |
| 安装返回成功但版本没变 | 系统安装器插了自己的确认，命令只对"请求"成功 |
| 服务端参数全变成空值或 -1 | 签名证书被当成了派生密钥，重签换了证书 |
| 清过日志后仍搜到旧崩溃 | 清空命令没覆盖事件缓冲区，读到的是历史 |
| 无墓碑的强杀 | 通过导入的终止调用 |
| 段错误 + 极小的故障地址 | 可能是**刻意安排**的崩溃，不来自空指针 |
| 终止信号 + 有墓碑 | 通常是真实断言 |
| 进程活着但库不在映射里 | 你的改动从未被加载 |
| 校验和错误（日志把真值打印在"expected"一侧） | 头里两个校验字段的**计算顺序**反了 |
| 安装失败码是裸数字、没有标准前缀 | 厂商系统把安装请求路由到了自家服务 |
| 等待首帧长时间阻塞 | 前台不是你的目标，首帧永远不会到 |
| 路径解析错误 / 变量没展开 | 宿主 shell 在到达设备前就展开了命令 |
| 编译非 ASCII 源码失败 | 缺编码参数 |

**两条读表纪律**：

- 见到"校验和错误"，**先查头再查被点名的类**——日志里的类名往往是无关的。
- 见到"无关类找不到"，**先怀疑容器与索引，不要怀疑那个类**。

## 环境与设备类

**设备坏了却怪改动。** 所有构建（包括零改动对照）都失败时，是设备状态、离线、
或重装后标识不匹配。**永远先跑零改动对照；对照也失败就停手。**

**宿主 shell 会吞掉设备命令。** 命令在到达设备之前就被宿主展开了变量、管道与引号，
于是设备收到的东西和你写的不是一回事。**把设备命令写进脚本再推上去执行。**

**安装报成功但装的是旧版。** 这是本域**最贵**的一个坑：陈旧行为被跨多轮测量，
每一次都像一个真实的负结果。**安装后必须证明产物变了**——
比对版本号或最后更新时间，或直接哈希设备上的产物。**没变就中止，不要测。**

**等一个需要人来推进的状态。** 轮询数分钟等一个不会自己到达的状态（同意、权限、
安装确认、验证码）。轮询看起来便宜而且"有进度"。
**等之前先问"什么会让它变"，答案是"人"就不要等**；设截止时间与不同的失败分支；
连续 N 次采样相同即判停滞。

## 工具类

**手写编码静默失败。** 自己拼装的数据结构（多层包装）漏一层就整段被忽略，
而且不一定报错。**用脚本编码，先强停进程再写，并保持属主一致。**

**轻信签名校验工具的结论。** 见上表。**要显式传入 SDK 范围参数**，
并用归档里有没有签名文件来交叉核实。

**按文件长度去重。** 同样长度的两份产物可以有完全不同的内容，其中一份可能结构已损坏。
**按内容哈希去重**；校验魔数与头偏移。

**自研脚本失败却看起来像结论。** 脚本吐出错表、错计数、"无匹配"，全都是错的。
真实代价：一个可用的提取器被打到 **30%**，而实际原因是参考数据不完整。
四道检查：

1. **先查形状合理性**——实测一个"平均每个偏移 31 个引用"的结果，
   而正常应约为 **3**，形状本身就该报警。
2. **用独立产物交叉**——两套独立实现一致到约 **99%** 才算证据。
3. **改阈值后重测**——在一个数量级范围内指标不动，说明那个旋钮根本没生效。
4. **注意名字遮蔽**——本地脚本文件名与标准库重名会静默改变行为。

**"扫描没找到调用点"被当成"不存在"。** 缓冲未对齐指令边界时解码器会**静默停止**，
残缺输出与"完整的负结论"无法区分。
**优先用字节模式或位模式扫描**，或按指令宽度重新同步；并且**声明所用方法与盲区**。

**解码失同步会让之后所有偏移全错。** 一条指令的宽度判错，后面全乱。
**断言遍历恰好终止于预期的结束位置**，用寄存器数量交叉验证，宽度表集中在一处。

## 构建与打包类

**剥掉整个 `META-INF/`。** 那里除签名外还存运行时服务注册，删了会导致启动即死，
报错却是"无关类找不到"。**只删顶层签名件，保留子目录。**

**等长替换不查排序。** 字节码的字符串表**必须有序**；等长替换保住了长度与偏移，
却可能落到邻居之间而失序，于是被整体拒绝。**替换值必须落在前后两个值的区间内**，
所以要跑排序守卫。注意：此时校验和与签名全部自洽，反汇编也能解——**没有任何其他信号会报警**。

**全树往返损坏优化过的字节码。** 汇编器无法复现编译器生成的合成桥方法，
而表级差异检查**全干净**。**做方法级外科改写，不要为了改一个方法重建整棵树。**

**同一个文件被改写两次。** 第二次序列化会丢掉第一次保留的元数据，症状是无 Java 异常的启动失败。
**一个程序、一次加载、合并全部改动、一次写回。**

**重签名会改变签名派生值。** 客户端常把签名材料喂给密钥派生函数；
换了证书，派生结果就变，服务端可能直接拒绝。
**改包后接口全失败时，先怀疑签名派生，再怀疑网络层。**
一个结构事实要记住：运行时拿到的签名字节与归档里的签名文件**不是同一段数据**
（实测分别为 **777** 字节与 **1199** 字节），不能互相代替。

**改完字节码后校验和不对。** 两个校验字段有**先后依赖**：
先算覆盖数据的签名，再算覆盖签名的校验和。顺序反了，头看起来合理但永不通过。
**每次改完都按序重算并断言。**

**对齐与压缩要求。** 资源表必须不压缩且数据偏移按 4 字节对齐；未压缩的库同理。
注意压缩归档的扩展区**最短 4 字节**，需要补 1–3 字节时**在该区域里无法表达**，
必须插入等长填充项。**用专门的签名工具**，通用打包工具的签名步骤会顺手重压缩、破坏对齐，
而它的校验仍然报成功。**靠读归档结构校验，不要靠退出码。**
