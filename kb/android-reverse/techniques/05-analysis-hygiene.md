# 分析卫生：脱敏、交接与侦察

用途：涉及"哪些内容可以写进交付文档"、"一次分析怎么交出去"、
"接手一个陌生目标从哪里开始"时读这一篇。它装的是**流程与边界**，不是分析技术。

**强度约定**：`[observed]` 有实测，`[inferred]` 由机制推出，`[unverified]` 为转述或假设。

## 脱敏与泄漏扫描

**核心规则**：改掉识别**目标**的，保留识别**技术**的。

判据只有一句话：**删掉它，还能不能教会这个技术？** 能教 ⇒ 保留；不能 ⇒ 改掉。

**必须保留**（改了就把知识变成了不可复用的个案）：

- 工具与库名（分析工具、反汇编器、系统库名）
- 函数与符号名（JNI 约定里的标准名字、运行时 API）
- 格式常量与协议字段名（编码类型名、wire type 名）
- 公开的漏洞编号
- 公开的练习样本与基准集名称及其官方地址
- 平台与 SDK 的包名前缀
- 本仓库自己的合成夹具标识
- 占位符（`<包名>`、`<设备>`、`<用户目录>`）
- 回环与模拟器地址（本机回环、模拟器网关）

**刻意不豁免**：文档专用地址段（RFC 5737 那几段）。
命中它就该报——因为真实代码里几乎不会出现文档地址段。
实测代价极低：在一个上百文件的仓库上，只有 **4 处**弱命中 `[observed]`。

**两条实现要求**：

1. **命中要带上下文**（前后各约 48 字符），**不要只报行号**。行号会随编辑漂移，
   上下文不会；而且报告本身如果只给行号，读的人还得回去翻。
2. **扫描器要分类**：包名 / 设备标识 / 令牌 / 应用密钥 / 端点 / 路径。

**状态要四态，不能只有成败**：

| 状态 | 含义 |
|---|---|
| `clean` | 无命中 |
| `leaks_found_strong_only` | 只有强命中 |
| `leaks_found` | 有弱命中 |
| `error` | 扫描器自身故障（基础设施问题） |

这与本套件的令牌协议一致（`0` 成功 / `1` 真实否定发现 / `2` 工具无法履职），
但多了一个中间态。**注意：多出来的那一态要用令牌区分，不要用退出码区分**——
退出码的语义是固定的，塞第三个含义会让调用方无法判断。

**放置位置**（顺序即优先级）：

- **不要只放在提交前钩子**里——长任务往往到最后才提交，那时已经晚了。
- 放进维护闸的例行检查。
- 发布前手工跑一次"显示豁免项"的模式，逐条确认豁免是合理的。
- **对即将发布的那份文件本身再扫一遍。**
- 持续集成里只扫**已发布的树**（本地工具目录默认排除在外）。

**自指证据（这条最有说服力）**：扫描器在**它自己的证据文件**里扫出了 26 处强命中 `[observed]`。
报告只要引用命中值，报告自己就成了泄漏副本。

**铁律：发布出去的文档永不引用命中值。** 只留规则、类别、强度、位置、计数；
值只用形状描述。

**三种典型误报**，写规则时先处理掉：版本号被当成 IP 地址（需要上下文词区分）；
纯数字的十六位串被当成序列号（要求含字母）；`x.split(".")` 这类代码被当成域名
（豁免需要整行匹配，不是词匹配）。

## 交接边界

**交付物形态决定验证方式。** 同一次分析，交付物不同，"做完"的含义就不同：

- **产物是文件** ⇒ 走验证阶梯（构建 → 安装 → 启动 → 行为 → 回归 → 分发副本一致）。
- **产物是运行期注入物** ⇒ 必须在目标自身的日志或指定构建上产生**可观察效果**。
  "装上了"、"管理器里启用了"**都不算**。
- **产物是本地服务 / 仿真** ⇒ 必须返回应用自己会产生的值，且你的测试框架能重连。
  "脚本加载成功"或"返回了某个值"**都不算**。
- **产物是分析报告** ⇒ 证据链 + 边界（未确定什么、以及为什么未确定）。

**第五边界，也是容易被忽略的一条**：
说一个工具或文档"已验证"，意味着它有**独立检查**——
第二实现、官方反汇编器、或字节精确往返。**工具自己测自己不算。**

**面向用户 vs 面向委托方要分开**：发布件里只放中性的机械信息（名称、版本、安装前提、
校验和、范围与免责声明）；把机制、改动点与推理留在分析报告里。

## 侦察顺序

按这个顺序做，每一步都有明确产出：

1. **身份**：包名、版本、SDK 区间、权限、组件清单。
   **不要手工从二进制 manifest 里解析包名**——字符串表里满是看起来像包名的类名前缀，
   实测有过把类名前缀误读成包名的案例。**两个独立来源必须一致**，非 ASCII 路径先转 ASCII。
2. **早快照配置面**：在深入之前先判断启动页 / 弹窗 / 分页是**客户端决策**还是**服务端数据**。
   这一步只要几分钟，却能提前区分"五分钟的活"和"死路"。
3. **加固判定**：读 `application android:name`（自有类 = 无壳；厂商类 = 壳；
   短且无意义的名字加 `appComponentFactory` = 整体壳）；
   字节码文件只有几十 KB ⇒ 真代码不在盘上；看 `lib/` 下有无壳库；
   高熵的 `assets/` 文件可能是伪装的图片；`assets/` 里出现第二个包或 jar。
   **即使形状很干净，也要写一行结论**。
4. **代码位置**：判断真代码在哪（字节码 / Flutter / Unity / Mono / RN / 纯原生），
   并定位应用自身包名所在的字节码文件，以最小化重建范围。
5. **SDK 清单**：按厂商分组（广告 / 分析 / 归因 / 设备标识 / 反调试 / 媒体）。
   **字符串里有不等于用了**。
6. **API 面**：基础地址、动态解析方式、路径、CDN、自定义头。
   硬编码的地址可能只是兜底。

**产出清单**（缺项就说明侦察没做完）：包名与版本与 ABI、是否加固及证据、
代码位置、应用代码在哪些文件里、SDK 及包装类、崩溃上报 SDK、反篡改位置、
API 基础地址与端点、设备计划。

## 工具不可用条件

**"工具报没有"不等于"目标没有"**——先用一个已知存在的项确认工具本可找到它。
以下条件会让工具静默失效：

- 无 schema 解码器缺失时的替代方案可用性有限。
- **只懂 HTTP/1.1 的代理看不到 gRPC 帧**（见协议篇）。
- 透明 TCP 代理对 QUIC 无效。
- 密钥日志方式对 Java 系 HTTP 客户端一般无效。
- 设备上的工具可能需要**界面手工启动**（命令行启不动），未启动时端口不监听；
  这时工具应当返回"无法履职"而不是"没有发现"。
- 只挂钩 Java 层的框架**进不了原生 `.so`**，对 Dart AOT 一类目标无效。
- 插桩服务端的版本与架构必须与目标进程匹配；加固目标要用启动时注入而不是附着。
- 构建工具会拒绝不存在的输出目录；资源链接工具缺平台描述文件时拒绝处理平台属性。
- **非 ASCII 的搜索目标**：某些工具遇到非 ASCII 会返回空，而空不等于不存在——
  先做一个"必中"的对照确认工具本身可用。

## 设备侧数据的一致性

改设备上的应用数据时，几个会让人误判"改动没生效"的机制：

- 改完必须**先强停进程**，否则内存里的副本会覆盖你的改动。
- 重装后应用 uid 会变，文件属主与安全上下文需要重设。
- 某些键值存储的实现带校验和，校验失败会**整库丢弃**——
  症状是"设置被重置"，而不是报错。
- 某些数据容器漏掉外层包装会直接崩溃。
- **收紧文件权限不能阻止改写**（应用可以删掉重建），
  而且这类锁是**设备状态，不随产物走**。
