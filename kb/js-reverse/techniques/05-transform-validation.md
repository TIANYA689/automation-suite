# 改写语义验证（JS 侧）

用途：任何"让代码更好看"的改写，都必须证明行为不变。

程序细节见 `js-script-deobfuscator` 技能的 `skills/js-script-deobfuscator/references/transform-validation.md`；本页给判据与反例。

## 核心命题

**AST 能定位语法结构，不保证改写后行为等价。**

反混淆工具（包括自动化工具）默认做的事情是"结构变换"，而 JS 的语义陷阱极多：隐式类型转换、`var` 提升、getter 副作用、求值顺序、`this` 绑定、词法遮蔽。任何一条被忽略，改写就是错的。

## 必查反例

| 改写动作 | 会破坏什么 |
|---|---|
| 常量折叠 | 双精度浮点、负零、NaN/Infinity、字符串拼接的隐式转换 |
| 按名字替换函数调用 | 词法绑定——局部 `atob`/`parseInt` 可能遮蔽全局同名函数 |
| 自动解码 Base64/hex 字面量 | 编码串可能是实际业务输入，不是"待解码数据" |
| 删除永假分支 | `var` 声明提升、块作用域、异常抛出时机 |
| 重写成员访问/调用 | `this`、getter 调用次数、求值顺序、可选链行为 |
| 展开代理函数 | 参数求值次数（`eq(a(), b())` 展开后可能多调一次） |
| 插入 trace | 序列化参数本身会触发 getter/`toJSON`，观测即改变 |

## 验证流程

```text
1. 原脚本 / 候选脚本 / 各自 hash / diff —— 四份分开保存
2. 从原脚本的真实执行结果构造期望值（禁止反向构造）
3. 一次只改一条规则
4. 比返回值、类型、异常三件事
5. 再用真实业务输入确认
6. 通过 → 保留；不通过 → 回退并记录反例
```

## 判定标准

| 结果 | 结论 |
|---|---|
| 所有样本返回值/类型/异常一致 | 在已测样本上等价，可保留 |
| 任一样本不一致 | 不等价，回退 |
| 无法构造有效期望值 | 标记"未验证"，不得判通过 |
| 只在部分样本一致 | 标记"条件等价"，写清条件 |

**"没报错"不等于"等价"。**

## 产物分类（交付时必写）

| 产物 | 性质 | 可否用于生产 |
|---|---|---|
| 原始脚本 | 权威副本 | 可（但不可读） |
| 验证通过的改写版 | 在测试样本上等价 | 需用户确认 |
| 分析副本（仅可读） | 未验证等价 | **否** |

把"分析副本"当"等价代码"使用，是解混淆交付最常见的严重事故。

## 与控制流还原的配合

还原控制流平坦化后，建议在还原前后各插入一次"状态序列日志"，比对序列是否一致。这比逐行读代码可靠，也能覆盖条件分支、循环边界与提前退出。
