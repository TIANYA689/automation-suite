# JSVMP 双路径决策

用途：遇到虚拟机保护的 JS 时，用最少的试错选对路径。

完整方法论见 `js-script-deobfuscator` 技能的 `skills/js-script-deobfuscator/references/jsvmp-paths.md`；本页是决策层。

## 核心认知

JSVMP 把业务逻辑编译成自定义字节码，由解释器在运行时执行。**因此静态阅读源码拿不到算法。** 任何"尝试读懂字节码"的努力都是弯路——这是本领域最常见的时间黑洞。

正确的问题不是"这段字节码是什么算法"，而是"这个签名函数的输入和输出是什么"。

## 两条路径

| 路径 | 适用 | 思路 | 相对成本 |
|---|---|---|---|
| A：算法追踪 | 签名经过可 hook 的原语；需要定位 I/O 边界 | 四板斧：Hook I/O → 插桩解释器 → 日志分析 → 源码级插桩 | 较高 |
| B：环境复现 | SDK 与环境强绑定；jsdom 能加载脚本 | 在 jsdom 里跑原始 VM，采集→对比→补丁，直接截获签名 | 较低 |

**默认先评估路径 B 的可行性**，因为它通常快约一个数量级。只有路径 B 明确不可行（脚本强依赖真实引擎特性）时才转路径 A。

## 路径 A 的四板斧分工

| 板斧 | 解决的问题 |
|---|---|
| 第一斧 Hook I/O | "VM 看外界"与"外界看 VM"：确定输入输出边界 |
| 第二斧 插桩解释器 | 定位字节码分发函数与关键调用链 |
| 第三斧 日志分析 | 从海量日志里反向追踪出公式 |
| 第四斧 源码级插桩 | "VM 看自己"：算法全部内联在分发循环里时的唯一观测手段 |

按问题选斧，不要求全开。前三斧够用时不必上第四斧（第四斧会改写源码，可能触发完整性校验）。

## 反向追踪法

处理海量日志效率最高的方法：

```text
从已知签名值出发
→ 搜索该值在所有日志中首次出现的位置
→ 反推：由哪个函数生成？该函数的输入是什么？输入从哪来？
→ 逐层向上直到原始明文输入
```

比"从头顺着读"高效得多，因为出口值唯一且可精确搜索。

## 路径 B 的六步

```text
0.5  确认签名函数入口（导出函数 / XHR 劫持 / fetch 劫持 / 配置驱动初始化）
      → 双通道必须都 Hook，漏一个就漏签名
1    在真实浏览器采集完整环境基线（分批，必须含 toString 系列）
2    在 jsdom 执行同一份采集代码
3    diff 并分级（致命 / 高危 / 中危）
4    按优先级打补丁，每修一项立即验证
5    在 jsdom 上下文内验证检测点
6    加载完整脚本触发签名 → 真实请求回归 ≥5 次
```

**服务端静默拒绝**（HTTP 200 + 空 body）是环境检测失败的典型信号，回到第 3 步重查致命级。

## 观察者效应

所有观测手段都会改变目标：

- Hook / Proxy 会改变原生性与对象身份。
- 源码改写会改变源码长度、堆栈形态与耗时，可被完整性检测发现。
- 高频日志会改变时序。

**纪律**：每装一个探针，都要能与无 Hook 基线对照。观测到的差异不一定是目标本身的差异。

## 无法完成时

记录事实、已尝试路径与剩余依赖，不伪造签名或成功响应。JSVMP 保护的设计目标就是提高成本，部分目标无法在合理时间内完全还原是正常结果。
