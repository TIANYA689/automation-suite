# APK Reverse Analysis

目标：回答"这个包的结构对不对、被加了什么保护、保护边界在哪一层、某个限制归谁所有"，
并且**每条结论都带强度标签与证据位置**。

## 范围边界（先读这一节）

**做**：结构事实与校验、改动审计、加固识别与边界度量、原生层加载行为与 JNI 形态识别、
无 schema 解码、门禁归属判定、脱敏与交付卫生。

**不做**：让某个校验不再生效、绕过完整性判定、规避检测、打破服务端授权。
遇到这类需求，先回到需求侧澄清**授权边界**，不要直接开工。
判定结论是"这个改不动"时，**那本身就是一个可交付的结果**，如实写出来。

## 强度标签（强制）

每条非显然的陈述都要带档位，禁止弱标签继承强标签的权威：

| 档位 | 含义 |
|---|---|
| `observed` | 跑过命令，输出在证据文件里 |
| `inferred` | 由机制或邻近测量推出，这一步本身没执行 |
| `unverified` | 假设的，或转述的，本仓库未复现 |

**"我推理出来了"是 `inferred`。** 详细口径见
`kb/methodology/techniques/04-coverage-and-limits.md`。

## 启动协议

1. **确认授权**：样本来源与授权范围。未确认授权的样本不做。
2. **盘点输入**：样本路径、大小、SHA-256、包名与版本、目标 ABI。
   **原件不动**，所有产物落在副本与 `exports/` 下。
3. **建立基线**：不改任何东西，只重签名，走一遍安装与启动。
   **这一步失败就停**——那是流水线或环境的问题，不是目标的问题。
4. **选路线**：按下面的四条路线之一进入，一次只做一条。
5. **写活记录**：把环境事实、已确认结论、死路、开放问题记下来。
   口径见 `kb/methodology/techniques/02-long-task-discipline.md`。

## 四条路线

### 路线 A · 结构审计与改动审计

适用：确认"改动只落在想改的地方"、判断重打包产物能否加载。

- 结构事实与校验手段：`kb/android-reverse/techniques/01-apk-and-dex-structure.md`
- 关键动作：结构差异比对 → 验证器合法性检查 → 设备首次执行；
  **等长替换是主要盲区**，所以每次改动必须声明目标方法签名。
- 收尾判据：`缺失集合 = 预期集合 − (Tier1 ∪ Tier2)` 必须为空；
  **验产物，不验工具的成功信息**。

### 路线 B · 加固与虚拟化识别

适用：目标"一改就死"，或需要给自有保护做强度自测。

- 识别判据、边界度量、方法体清空比例：`kb/android-reverse/techniques/02-hardening-identification.md`
- 关键纪律：**单变量**，一次只改一个变量、每次走完整安装启动；
  **边界通常不均匀**，不要用一个结论概括整层。
- 能力上限要写清楚：干净的静态读数只许可"这不是 dex 虚拟化"，
  **不许可"这没有加固"**。

### 路线 C · 原生层与 JNI

适用：符号搜不到、库没被加载、或需要判断保护实现在哪一侧。

- ELF / 链接器 / JNI 事实与实测边界：`kb/android-reverse/techniques/03-native-layer.md`
- 关键动作：先看**活进程的实际映射**（属性查询只是预测），
  再判 JNI 形态；**动态注册会让符号搜索静默失败**。
- 需要符号级静态恢复时转 `binary-symbol-recovery`；
  需要在无设备条件下跑片段时转 `emulated-execution-debug`。

### 路线 D · 协议与归属判定

适用：流量解不开，或需要判断某个限制能不能在客户端侧达成。

- 无 schema 解码、gRPC 帧、QUIC 限制、归属矩阵：
  `kb/android-reverse/techniques/04-protocol-and-attribution.md`
- 关键纪律：**先定服务端权威，再动客户端**；
  值在 200 响应里缺失 ⇒ 客户端改不动，如实记录。

## 交付与验收

报告模板见 [分析报告模板](references/analysis-report-template.md)。

最低要求：

- 每条结论带强度标签与证据位置（文件 / 命令 / 行号）。
- **零改动对照**至少做过一次。
- 明确写出**残留**：没有确定什么、以及为什么没确定。
- 面向用户的说明与面向委托方的报告**分开**：发布件只放中性的机械信息。
- 交付前做脱敏检查，口径见 `kb/android-reverse/techniques/05-analysis-hygiene.md`。

**"工具报没有"不等于"目标没有"**——先用一个已知存在的项确认工具本可找到它。

## 失败处理

| 情况 | 处理 |
|---|---|
| 零改动基线就失败 | 停。修流水线或环境，不要调目标 |
| 安装被拒 | 失败码是一个家族，读冒号之后的文本；先比对签名与对齐 |
| 改了之后崩溃 | 先做零改动对照，再逐项回退做二分 |
| 符号搜索零命中 | 先排除动态注册与可见性设置，再怀疑"不存在" |
| 度量比例低 | **低比例不是排除证据**，只有高比例是确认证据 |
| 同一变量两次相同失败 | 停，不要试第三个参数 |
| 目标是真虚拟化保护 | 直说停止点与成本量级，不要给"研究计划"当配方 |
| 无法确定 | 写"不确定"并说明还缺什么证据，不编造结论 |

## Related Skills

- `binary-symbol-recovery`：去符号二进制的函数定名、结构体重建、调用图整理。
- `emulated-execution-debug`：无设备条件下执行机器码片段，验证静态结论。
- `js-script-deobfuscator` / `python-script-decryptor`：脚本级混淆还原与包装解密。
- `automation-architect`：需求不清、授权边界不明、或多技能协同时的上层路由。
- `knowledge-architect`：把可复用的识别规律回写 `kb/android-reverse/`。
