# Knowledge Architect

把一次成功经验变成未来仍然有用的系统知识。知识不是“把本次过程全文复制进 Skill”，而是经过证据筛选、去项目化、正确路由、最小实现和验证后的可复用资产。

## 核心原则

1. **证据先于抽象**：没有成功结果、失败对照或重复实例，不把猜测升级为规则。
2. **动态发现优于手工总表**：扫描当前 Skill 与资源，不维护容易过期的版本和 Pattern 镜像。
3. **单一知识源**：知识写到真正负责它的地方，其他位置只引用，不复制全文。
4. **项目知识默认留在项目**：只有稳定、可迁移、可执行的经验才进入全局 Skill。
5. **提案先于跨域修改**：修改用户级目录、多个 Skill、工作流或长期记忆前设置检查点。
6. **可验证、可撤销**：每次固化都要说明验证方法、影响范围和回滚方式。

## 不自动触发

以下情况不要自行“反哺系统”：

- 用户只是称赞结果，未要求保存经验；
- 普通代码修复、重构或文档润色；
- 仅对一个 Skill 做结构/触发优化，此时使用 `skill-creator` 或 `darwin-skill`；
- 一次性项目参数、接口、账号格式、活动状态、排错日志；
- 未经明确请求写入长期记忆或用户级配置；
- 为保持索引“看起来完整”而复制其他 Skill 的内容。

## 输入与证据

开始时收集：

- 用户希望沉淀的任务、决策或经验；
- 成功产物、测试结果、错误修复前后对照；
- 经验出现过的独立场景数量；
- 当前项目与可写知识目录；
- 候选知识的受众、稳定期和维护责任；
- 用户是否授权修改项目外文件、多个 Skill 或长期记忆。

如果只有模糊评价，例如“这次做得不错”，询问是否需要固化；不要直接改文件。

## 资源

- 需要确定知识落点时读取 `references/knowledge-routing.md`。
- 需要记录候选、证据和决策时使用 `references/candidate-schema.md`。
- 需要获取当前技能清单时运行 `scripts/inventory_skills.py`，不要依赖本文件中的静态版本表。
- 修改后使用 `evals/trigger-evals.json` 和 `evals/output-evals.json` 检查边界与质量。

## 工作流

### 1. 建立候选

把经验写成一个可检验命题：

```text
当 <可观察条件> 出现时，
执行 <具体动作>，
因为 <机制或约束>，
用 <测试/指标> 验证。
```

同时记录来源任务、证据文件、成功/失败结果和已知例外。不要从最终结果反推不存在的因果关系。

### 2. 通过通用性门

按以下顺序判断：

| 检查 | 通过标准 | 未通过处理 |
|---|---|---|
| 可迁移性 | 至少两个独立场景，或属于稳定的语言/框架机制 | 留在项目文档 |
| 稳定性 | 不是短期接口、版本偶然行为或一次性配置 | 标注观察项，不进入全局规则 |
| 可执行性 | 能写成条件、动作、验证 | 保留为背景说明或不固化 |
| 去项目化 | 删除名称后仍保持有用且不失真 | 保留原项目上下文 |
| 安全性 | 不含秘密、未授权行为或危险默认值 | 脱敏、限制范围或拒绝固化 |
| 所有权 | 能确定维护它的 Skill/项目 | 先解决归属，不创建重复副本 |

“看起来通用”不算证据。无法通过时，把结论和原因写入项目 README、决策记录或任务报告。

### 3. 动态发现现状

扫描实际技能根目录：

```powershell
python scripts\inventory_skills.py `
  "$HOME\.codex\skills" `
  --output inventory.json
```

检查：

- 名称、description、路径和资源；
- 重名 Skill；
- 缺失 frontmatter；
- 超长文件；
- 已存在的职责归属；
- 相邻 Skill 是否只是引用关系，而非同步副本。

如果无法读取某个根目录，报告扫描范围；不要把未扫描区域当作不存在。

### 4. 选择知识落点

按最小作用域选择：

1. **项目 README / docs / ADR**：项目约束、业务字段、接口、一次性决策。
2. **现有 Skill 主体**：稳定且每次执行都必须遵守的核心步骤或边界。
3. **Skill `references/`**：详细模式、背景知识、变体表和按需读取内容。
4. **Skill `scripts/`**：重复、确定、可测试的机械操作。
5. **Skill `assets/` 或模板**：固定输出骨架、样式和可复用素材。
6. **新 Skill**：没有现有所有者，且存在独立触发场景、完整工作流和持续复用价值。
7. **长期记忆**：只有用户明确要求且当前运行环境允许时；遵循该环境的记忆写入规则。

不要因为某知识同时影响多个 Skill 就复制到多个主体。优先确定一个权威来源，其他 Skill 添加短引用或路由说明。

### 5. 形成变更提案

修改前展示：

```markdown
## 知识固化提案
- 候选命题：
- 证据：
- 通用性结论：
- 权威落点：
- 计划修改：
- 不修改：
- 验证方式：
- 风险与回滚：
```

提案要列出具体文件和预期行为变化，不使用“全面同步”“完善生态”等模糊措辞。

### 6. CHECKPOINT / STOP

以下任一情况必须等待用户确认：

- 修改当前项目之外的用户级或全局目录；
- 一次修改两个及以上 Skill；
- 创建、删除、移动或重命名 Skill；
- 更新长期记忆、工作流、自动化规则或系统配置；
- 覆盖与当前任务无关的用户改动；
- 候选证据不足但用户仍希望升级为全局规则；
- 变更涉及安全、法律、凭据、网络访问或高影响默认行为。

用户只批准部分范围时，严格缩小变更集。

### 7. 实施最小变更

确认后：

1. 重新读取目标文件，保留并融合现有用户改动；
2. 修改权威来源，删除或替换已确认的冲突规则；
3. 只在必要位置添加引用，不维护重复版本号/Pattern 镜像；
4. 遵循目标 Skill 的已有结构和版本约定，不强制所有 Skill 使用同一 frontmatter；
5. 新增脚本时保持单一职责、明确输入输出和失败退出码；
6. 更新目标目录 README，记录日期、原因、验证和限制；
7. 不顺手重构无关内容。

### 8. 验证

至少验证：

- frontmatter 可解析，名称与目录职责一致；
- 所有相对链接和资源路径存在；
- 新规则有清晰触发条件、动作、例外和失败分支；
- 没有泄露 token、账号、内部地址或项目专属数据；
- 触发正例能命中，近邻负例不会误触发；
- 脚本或模板通过无害样例测试；
- 修改范围与用户批准一致；
- README 和变更记录已更新。

对跨技能变更，分别验证每个 Skill 的独立职责，不以“内容已经同步”代替测试。

### 9. 记录决策

交付以下摘要：

```markdown
## 固化结果
- 新知识：
- 权威来源：
- 引用位置：
- 拒绝/保留在项目的内容：
- 验证：
- 未验证与后续观察：
```

保留候选证据和拒绝原因。被拒绝的知识不是失败，它避免了全局规则被一次性经验污染。

## 失败处理

| 触发条件 | 一线处理 | 仍失败时 |
|---|---|---|
| 找不到明确归属 | 比较现有 Skill 的 description 与工作流所有权 | 保留在项目文档并列为待观察候选 |
| 多个 Skill 都可承载 | 选择拥有执行责任的一方作为权威来源 | 设置 CHECKPOINT，请用户确认所有权 |
| 证据只有一次成功 | 提炼为项目级经验并记录验证条件 | 等第二个独立实例后再升级 |
| 目标文件与清单不一致 | 重新扫描实际目录和 frontmatter | 报告扫描盲区，不更新静态镜像 |
| 用户改动与候选冲突 | 停止写入并展示差异 | 由用户选择合并、保留或取消 |
| 跨技能同步失败 | 保留已验证的权威来源，不复制半成品 | 报告未完成引用，逐个修复后再验证 |
| 脚本测试失败 | 保留失败输出并修复最小问题 | 回滚脚本变更，改用文档化流程 |
| 发现秘密或敏感数据 | 立即停止传播并脱敏 | 不固化原文，只记录安全规则 |

## 反模式黑名单

- 不把一次性成功包装成“最佳实践”。
- 不维护手工复制的全技能版本与 Pattern 总表。
- 不因用户称赞而自动修改全局文件。
- 不把项目域名、接口、状态、Cron、账号格式写进通用 Skill。
- 不要求所有 Skill 强制使用同一种章节或版本字段。
- 不在多个 Skill 中复制同一长段规则。
- 不为新知识强行创建新 Skill。
- 不用“同步完成”代替路径、语法、触发和行为验证。
- 不未经明确请求写入长期记忆。
- 不删除冲突证据或覆盖用户未提交改动。

## 与其他技能的边界

- `skill-creator`：创建或优化单个 Skill 的内容、description 和评测。
- `darwin-skill`：按质量量表评估并迭代 Skill。
- `skill-refactor`：精简过长、重复、上下文成本高的 SKILL.md。
- `knowledge-architect`：决定经验是否值得固化、写到哪里，以及跨知识资产如何保持单一来源。
