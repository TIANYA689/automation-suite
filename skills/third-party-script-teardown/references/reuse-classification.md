# 复用分档判据

用途：把"这个写法值得抄吗"从一个感觉问题变成四个可判定的档位。
`scripts/misc/script_teardown.py` 给的是**默认档**；本文件是复核它、升降它的判据。

## 为什么必须分档

一个跑得通的脚本可以同时包含值得抄的编排结构和绝不该抄的凭据硬编码。
不分档的"学习笔记"会把两者一起搬进来——而搬进来之后，没人会再回头查第二遍。

**分档的成本是几分钟；不分档的成本是下一次泄露或下一次线上事故。**

## 四档判据

### `direct` 直接复用

**定义**：语义固定、无目标站点假设、本项目已有 Pattern 完整覆盖。

必要条件（全中才算）：

1. 换个目标站点它依然成立（超时、退避、原子写、脱敏、配置双源）。
2. 本项目的 Pattern 已经覆盖它的语义，抄过来不需要新增契约。
3. 它的实现里没有目标站点特有的名字、字段、路径。

**典型**：`timeout=`、`Retry(...)` 结构、`Config` + 环境变量覆盖、脱敏函数、
并发锁、配套文件组织（README / `.env.example`）。

**反例（看起来像 direct，其实不是）**：
- `timeout=8` —— 数值是目标站点的经验值，结构可抄，**数值必须重新取值**。
- `except Exception: pass` 的"稳健"写法 —— 它吞错，进 `refuse`/`caution`。

### `adapt` 改造后复用

**定义**：思路成立，但它的形态依赖本项目不具备（或不该具备）的前提。

必要条件（至少一条）：

1. 接口形状不同（账号分隔符、通知渠道、日志字段）。
2. 它假设了一个本项目不保证的运行环境（青龙 `notify`、特定目录、特定 Python 版本）。
3. 它的分层与我们的分层对不上，需要重新切。

**典型**：账号解析、代理接入、通知推送、日志形态、缓存结构。

**必做**：写清**改哪一点**。只写"需要改造"等于没写——下一个人还得重新判一次。

### `borrow` 只可借鉴

**定义**：只能借**思路与形状**，实现必须重写。

必要条件（至少一条）：

1. 实现与目标站点的密钥、算法、字段绑定（签名、设备指纹、加密）。
2. 实现依赖了我们无法确认的外部假设（服务端时间、字段顺序、Cookie 容器）。
3. 它的"聪明"来自对目标系统内部行为的观察，换个系统就不成立。

**典型**：设备指纹生成、签名算法、多阶段协议划分、任务编排形状、拟人延迟分布。

**必做**：把"思路"和"实现"分开写。借的是"先算 `startTime + duration - serverTime`
再等"，不是那行代码。

### `refuse` 拒绝吸收

**定义**：吸收它会降低安全机制、引入合规风险或带来不可控副作用。

命中任意一条即 `refuse`：

| 类别 | 例子 |
|---|---|
| 凭据硬编码 | 源码里的 `token = "..."`、`Authorization: Bearer <真值>` |
| 风控绕过 | 验证码伪造、`bypass`、隐藏验证行为 |
| 凭据进入日志 / URL | 代理账号密码拼进 URL、Bearer 值直接打印 |
| 保护侧能力 | 反调试、自防御、代码虚拟化——属于保护技能，不属于拆解 |
| 版权与来源 | 上游 GPL 代码原样复制、预编译二进制 |

**`refuse` 不是"不看了"。** 它是"我看懂了它，并决定不吸收"——必须写进报告，
连同**为什么**。沉默的跳过与没注意到，在下一个人那里无法区分。

## 升降档

工具给的是默认档，判定依据是"这个维度**通常**属于哪一档"。实际项目里要按语境调：

| 场景 | 默认 | 调整 | 理由 |
|---|---|---|---|
| 目标脚本的签名实现 | `borrow` | **不降** | 抄了就是把别人的密钥体系搬进来 |
| 目标脚本的账号解析 | `adapt` | 可以 → `direct` | 如果它用的分隔符与本项目契约一致 |
| 目标脚本的 `Config` | `direct` | 可以 → `adapt` | 如果它把凭据写进了配置区（那就是 `refuse` 那一条） |
| 目标脚本的日志 | `adapt` | 可以 → `borrow` | 如果它的日志形态与本项目规范冲突 |
| 目标脚本的并发 | `adapt` | 可以 → `borrow` | 如果它靠"账号顺序"隐式保证正确性 |

**降档必须给理由。** 理由写不出来，说明调的是偏好而不是判断。

## 与「吸收纪律」的对接

上游吸收那条纪律（见 `.workbuddy-ai/memory/rules/07-吸收纪律.md` 第 37 条）的切法是问
**"是搞清楚状态，还是改变状态"**。本技能沿用同一条切法：

- **吸收**：测量 / 记录 / 对照 / 回滚 / 结构归档 / 验证 —— 这些让状态**更可见**。
- **不吸收**：降低安全机制、绕过校验、隐藏行为 —— 这些让状态**更不可见**。

差异在于对象：吸收纪律针对**仓库**，本技能针对**一个脚本**。
两者共用同一条判断线，不各写一套。

## 判定清单

对每个候选维度逐条过：

- [ ] 换个目标站点它还成立吗？（不成立 → `borrow`）
- [ ] 它的接口形状与本项目契约一致吗？（不一致 → `adapt`）
- [ ] 实现里有没有凭据、密钥、目标站点专属名字？（有 → 至少 `borrow`，凭据 → `refuse`）
- [ ] 它有没有降低任何安全机制？（有 → `refuse`）
- [ ] 它的"聪明"来自可迁移的机制，还是来自对某个系统内部的观察？（后者 → `borrow`）
- [ ] 降档了吗？理由写出来了吗？

## 反模式

- 因为"跑得通"就整段照搬。
- 把 `refuse` 项从报告里删掉，只留"值得学习的部分"。
- 复用候选里混进压缩 / 混淆文件的命中（那里面没有可读的范本）。
- 档位一栏全填 `direct`——通常意味着没有真的分档。
- 用"更优雅""更规范"代替 Pattern 依据。
