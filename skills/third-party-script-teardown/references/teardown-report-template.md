# 拆解报告骨架与呈现规范

用途：拆解结论要能**被人扫一遍就用**，也要能**被下一个人复核**。
本文件规定报告骨架、排版纪律，以及"输出日志美化"在拆解场景里的落点。

## 一、报告骨架

落盘到 `reports/third-party/<日期>-<目标名>.md`。骨架可直接抄：

```markdown
# <目标名> 拆解 —— 一行点出结论，不是一行描述活动

## Metadata
| 字段 | 值 |
|---|---|
| 材料来源 | 从哪来、是否授权、是否只读 |
| 分析深度 | 只读结构 / 读懂逻辑 / 复现算法 |
| 规模 | 文件数、可读 / 压缩 / 混淆 / 静态库 / 读不出 |
| 工具证据 | `exports/third-party/teardown.json`（含行号） |
| 未覆盖 | 没读的文件、没验的假设 |

## 结论（先写这段）
三到五条。每条一句话，带档位或行号。例如：
- 基础设施层写得规整，配置双源与重试分层可以直接复用（`direct`）。
- 签名与设备指纹与目标站点强绑定，只能借鉴编排形状（`borrow`）。
- 有一处凭据硬编码与一处风控绕过，**明确不吸收**（`refuse`，见第 5 节）。

## 1. 结构清单
| 文件 | 类型 | 行数 | 说明 |
|---|---|---|---|
只列可读的与非可读的代表；全量在 JSON 里。

## 2. 逻辑分层
### 2.1 基础设施
| 维度 | 命中位置 | 它怎么做 | 本项目对应 |
### 2.2 业务逻辑
只记编排形状：顺序、分支、幂等边界。
### 2.3 规避逻辑
只记机制，不复用实现。

## 3. 复用分档
| 档位 | 维度 | 证据（文件:行） | 复用时要注意 |
四档都要出现；`refuse` 一节不允许为空（为空要写"逐项检查过，无"）。

## 4. 对照重写：我会怎么做
| 维度 | 别人的做法 | 我会怎么做 | 为什么不同 | 依据 |
依据必须是 Pattern 编号或明确标成"偏好"。

## 5. 拒绝吸收
| 项 | 位置 | 为什么不能抄 |
逐条写理由。这是报告里最容易被删、也最不该删的一节。

## 6. 知识回填候选
| 候选命题 | 建议去处 | 证据 | 通用性结论 |
去处：`kb/<领域>/techniques/` / `kb/ai-findings/findings.jsonl` / 仅留本报告。

## 7. 未验证与未覆盖
明确写出：哪些结论只是推断、哪些文件没读、哪些假设没验。
**"缺口"要注明来源**：需求不同（它本来就不需要）/ 没有材料（后缀不在范围）/
读了看不进去（加密载荷）/ **检测器没实现这门语言的写法**。
最后一种尤其要写：一个纯 JS 项目报出大量缺口时，先核 `teardown_rules.py` 里
那些维度的 `langs` 声明与 `regexes` 实际写了哪几种语言，再决定要不要说"它没有"。
```

## 二、呈现纪律

### 结论先行

读者第一屏要拿到结论，不是拿到过程。`## 结论` 必须在 `## 1. 结构清单` 之前——
把结论放在 300 行之后，等于没写结论。

### 一条断言一个分级

沿用 `kb/methodology/techniques/05-precedent-records.md` 的三档：

| 分级 | 含义 |
|---|---|
| `observed` | 跑过命令、看过那一行，行号在证据里 |
| `inferred` | 由机制推出，没有直接观测 |
| `unverified` | 没验，但值得记 |

**`observed` 只留给有行号在背后的断言。** "它的重试是分层的"如果只是扫了一眼，
那是 `inferred`。含糊不是礼貌，是把复核成本推给下一个人。

### 对齐按显示宽度，不按字符数

中文标签是双宽字符。`f"{'配置集中':<10}"` 补的是字符数，4 个汉字占 8 列，
于是它和 6 个汉字的标签在屏幕上差 4 列——**整列歪掉的表会被当成随手拼的输出**，
而"看起来不可信"和"不可信"在交接时的后果一样。

工具侧已经处理（`display_width` / `pad`）；手写报告里的表格靠 Markdown 渲染对齐，
不要在纯文本里手数空格。

### 数字要给口径

"文件 12 个"要说清是**扫到的**还是**全部**的。跳过多少、为什么跳过，
和被统计的数字一样重要——`skipped_noise` 是"本来就不该看"，
`skipped_suffix` 是"后缀不在范围"，两者都不是"这个脚本没有能力"。

### 脱敏是默认，不是选项

- 长不透明串、邮箱、手机号：输出前掩码。
- 凭据类命中：**只报行号，不报片段**。报告会被贴进对话、写进笔记；
  片段里带真值，泄露就发生在"检查"这个动作里。
- 真实域名：只写结构（`<站点>/api/<动作>`），不写完整 URL。
- **掩码是降噪与防误贴，不是安全边界**（同 `har_source` 的纪律）。挡的是顺手抄，挡不住刻意规避。

### 长度预算

一份拆解报告正文控制在 **150 行以内**。超了说明在复述代码而不是在给结论——
把细节挪进 JSON 证据文件，报告里只留判断。

## 三、输出日志的美化

分两处，**不要互相复制**：

### 3.1 工具侧：`script_teardown.py` 的渲染

规范（已实现，改它要同步本文件）：

- 标题框 → 目标与口径 → 分节（`── N. 标题 ───`，破折号补到整宽）→ 提示 → 结论。
- 每节用显示宽度对齐，列宽由内容决定。
- 控制台编码画不出制表符时**自动退回 ASCII**，而不是抛异常或印乱码。
- 默认输出**掩码片段**，`--no-snippets` 可完全关掉。
- 机器可读走 `--json` / `--out`，人读走默认文本——两者内容一致，不各写一套。

### 3.2 脚本侧：拆解结论落地成新脚本时

**本文件不复制脚本日志规范。** 唯一事实源是：

- Python：`skills/automation-script-dev-py/SKILL.md` 的 P11 / P11.1 / P11.2
  （状态卡片、汇总表、脱敏、线程安全日志）。
- JavaScript：`skills/automation-script-dev-js/SKILL.md` 的 P8.5。

拆解场景**额外**要注意的两点：

1. **把别人的日志形态当反面教材**。第三方脚本里常见的"每行裸 print 带完整 token"
   是 `refuse`/`adapt` 的典型对象，不要因为"它跑得好好的"就继承。
2. **在对照重写表里给出日志一行**。日志是最容易被"以后再说"的一层，
   而它恰恰是交付后唯一还在被人看的东西。

## 反模式

- 结论写在最后，或者干脆没有结论，只有过程。
- 表格里出现"设计优雅""写得很规范"这类无法复核的词。
- 断言全标 `observed`。
- `refuse` 一节为空，且没有说明"检查过、无"。
- 报告里出现真实域名、账号、Token。
- 把 `script_teardown.py` 的 JSON 输出整段贴进报告充当分析。
