# Third-Party Script Teardown（第三方脚本拆解）

读别人的脚本，产出**四样可复核的东西**：它怎么写的、用了什么逻辑、哪些值得我复用、
我自己写会怎么做。最后一步把值得留下的部分变成知识库候选。

本技能存在的理由：**"值得复用"和"能跑通"是两件事。** 一个跑得通的脚本可以同时包含
值得抄的编排结构和绝不该抄的凭据硬编码。不做分档的"学习笔记"会把两者一起搬进来。

## 不做什么

| 不做 | 去哪 |
|---|---|
| 解混淆 / 脱壳 / 还原被保护的代码 | `js-script-deobfuscator` / `python-script-decryptor` |
| 把别人的脚本改成能跑 | `automation-script-dev-py` / `automation-script-dev-js` |
| 分析二进制 / APK | `binary-symbol-recovery` / `apk-reverse-analysis` |
| 直接把结论写进知识库 | `knowledge-architect`（本技能只出**提案**） |
| 从上游仓库提炼工程能力 | `upstream-absorption`（那条流程针对仓库，这条针对脚本） |

**目标脚本一律只读。** 不导入、不执行、不安装它的依赖。理由不是洁癖：第三方脚本的
模块级代码可能建文件、连网、读凭据、`sys.exit`，而拆解的全部价值在于"我看了它"，
不在于"它跑了"。

## 授权与边界（阶段 0，不可跳过）

开工前明确写下：

1. **材料来源**：脚本从哪来（公开仓库 / 他人交付 / 授权样本），是否允许分析。
2. **分析深度**：只读结构 / 读懂业务逻辑 / 复现算法。三者代价差一个数量级。
3. **产物边界**：结论能不能进仓库。**抓包派生物与真实凭据一律不进仓库**（见 `AGENTS.md` 硬性约束）。
4. **不做的事**：不实现绕过、不伪造验证、不复制上游受版权保护的代码。

来源不明或授权不明时**先澄清**，不要用"只是看看"开工。

## 工作流

### 阶段 1 · 结构盘点（先拿证据，再下判断）

```bash
# 只读盘点：结构清单 + 能力矩阵 + 复用候选 + 缺口 + 风险
python scripts/misc/script_teardown.py <目标目录> --json --out exports/third-party/teardown.json
python scripts/misc/script_teardown.py <目标目录>            # 人读版
python scripts/misc/script_teardown.py <目标目录> --no-snippets
```

工具产出五张表（口径与判据见 `kb/code-reading/techniques/01-teardown-workflow.md`）：

| 表 | 回答什么 | 不能拿它当什么 |
|---|---|---|
| 结构清单 | 有哪些文件、可读 / 压缩 / 混淆 / 静态库 / 读不出 | 不是"质量评分" |
| 能力矩阵 | 命中哪些维度、在第几行 | 命中 ≠ 写得好，行号要自己回看 |
| 复用候选 | 按四档归位 | 默认档位，不是最终裁定 |
| 缺口 | 本项目有 Pattern、它没有 | 缺 ≠ 差：需求不同也会缺 |
| 风险 | 明确不吸收的写法 | **每个文件只报首处**，不是全量；同一条规则在多个文件里命中会各占一行 |

**检测维度与风险规则是数据，在 `scripts/misc/teardown_rules.py`。**
加一个维度只改那张表；引擎 `scripts/misc/script_teardown.py` 不随维度数量增长。
散文区间（注释 / 文档字符串的识别与等长抹除）在 `scripts/misc/text_spans.py`，
人读版的排版（列宽、按显示宽度截断、`--ascii` 回退）在 `scripts/misc/teardown_render.py`。
「文本怎么切」「命中什么维度」「报告长什么样」是三件事，分三个文件、三条变更轴。

工具是启发式，六条纪律必须照做：

- **逐条回看命中行**。行号是唯一能被复核的证据，不看就等于抄了工具的结论。
- **压缩 / 混淆 / 静态库只当信号**。它们不进复用候选——范本必须来自可读代码。
- **"没命中"与"没材料"分开说**。空目录、后缀不匹配、解码失败都不是"它没有这个能力"。
- **"读了但看不进去"是第三种情况**。加密 / 打包载荷（自解密脚本的密文段、
  `exec(base64…)` 的载荷）关键词彻底看不见，**美化器对它无效**。工具会点名这类文件；
  看到就得把它的 0 命中读成"要先去解密"，不是"它什么都没有"。
- **注释里的关键词不算证据**。工具已做去散文过滤并在提示里报出过滤次数；
  被过滤的维度会落进"缺口"，不是"没有"。若怀疑误杀，回原文核对那几行。
- **裸词命中要看清是"实现"还是"提示语"**。`脱敏` / `进度` / `多账号` 这类词
  出现在 `print("...")` 里的概率不低，而**字符串字面量不在散文过滤范围内**
  （`"User-Agent"` 是实打实的协议证据，剔了就是静默假阴性）。
  工具已把这类词锚到定义位置（`def …脱敏`），但看到命中仍要回原文确认那一行是代码还是文案。
- **"缺口"不等于"目标脚本没有"——它可能只是检测器没写这门语言的写法**。工具覆盖
  Python / JS / TS / shell / PowerShell / batch 六种后缀，但**各语言的维度覆盖度不均衡**：
  Python 最全，JS 次之，其余三种只有少数维度写了对应写法。核对方式是看
  `teardown_rules.py` 里该维度的 `langs` 声明与 `regexes` 实际写了哪几种语言——
  **声明覆盖不等于实现覆盖**（`ALL_LANGS` 只表示"这个维度对所有语言都适用"，
  不表示"每条正则对所有语言都命中"）。同名不同形是最常见的漏法：
  `timeout=` 与 `timeout:`、`while True` 与 `while (true)`、`def mask(` 与 `function mask(`。

### 阶段 2 · 逻辑提取（把代码分成三层）

按层读，不要按文件顺序读：

| 层 | 装什么 | 阅读重点 |
|---|---|---|
| **基础设施** | 配置、账号、请求封装、重试、代理、并发、缓存、日志、通知 | 这一层最值得复用，也最容易抽出通用模式 |
| **业务逻辑** | 签到、领取、下单、上报等目标站点特有的步骤 | 只记**编排形状**（顺序 / 分支 / 幂等边界），不记站点细节 |
| **规避逻辑** | 设备身份、签名、验证码、风控绕行 | 只判断"它用了什么机制"，**不复用实现** |

对每个非平凡函数回答三问：

1. 它的**输入契约**是什么（谁给它什么、缺了会怎样）？
2. 它的**失败路径**是什么（异常往哪去、会不会被吞）？
3. 它**依赖的外部假设**是什么（服务端时间、字段顺序、Cookie 容器）？

写不出这三条的函数，说明还没读懂——**不要把"没读懂"写成"设计简洁"**。

### 阶段 3 · 复用分档

四档，逐项判定（完整判据与反例见 `references/reuse-classification.md`）：

| 档位 | 含义 | 典型对象 |
|---|---|---|
| `direct` 直接复用 | 语义固定，本项目已有 Pattern 完整覆盖 | 超时、重试结构、配置双源、脱敏函数 |
| `adapt` 改造后复用 | 思路对，但要换成本项目契约 | 账号格式、通知渠道、代理接入、日志形态 |
| `borrow` 只可借鉴 | 只能借**思路**，实现必须重写 | 设备指纹、签名、协议阶段划分、编排形状 |
| `refuse` 拒绝吸收 | 降低安全机制或引入风险，**明确不吸收** | 硬编码凭据、风控绕过、代理凭据进 URL、反调试 |

两条硬规则：

- **`refuse` 项必须写进报告，不能默默丢掉。** "我看过它、我决定不抄"和"我没注意到"
  在下一个人那里是两件事；只写前者，才算把判断交接出去。
- **档位可升可降，但必须给理由。** 工具给的是默认档；降档（`direct` → `adapt`）
  说明目标脚本的写法依赖了本项目不具备的前提。

### 阶段 4 · 对照重写（"我来写会怎么做"）

不是重写一份脚本，是写一张**差异表**——这才是能交接的东西：

| 维度 | 别人的做法 | 我会怎么做 | 为什么不同 | 依据 |
|---|---|---|---|---|
| 配置 | 单文件常量 | Top-Level 双源 + 环境变量覆盖 | 本地与青龙要同一份代码 | PY-P9.1 |
| 重试 | 固定 3 次 sleep | 分层重试 + 代理刷新 + 账号级熔断 | 网络失败与业务失败要分开归因 | PY-P6.1/P6.3 |
| 日志 | 裸 print 带 token | 状态卡片 + 汇总表 + 脱敏 | 用户是"扫"不是"读"，且日志会外传 | PY-P11/P11.1 |

规则：

- **每行必须有 `依据`**。填不出 Pattern 编号的，说明这是个人偏好而不是工程结论——
  那就标成"偏好"，不要伪装成"更优"。
- **不改写业务逻辑**。别人对目标站点的理解可能比规则更准；只对基础设施层下判断。
- **能不动就不动**。差异表里没有"我全都会重写"这个选项。
- 差异表落盘到报告；需要真出代码时，转 `automation-script-dev-py` / `-js`。

### 阶段 5 · 知识回填提案

拆解不产生知识库内容，只产生**候选**。三档去处：

| 候选形态 | 去哪 | 判据 |
|---|---|---|
| 可写成"当 X 出现时做 Y，用 Z 验证" | `kb/<领域>/techniques/` | 至少两个独立场景 / 可执行 / 去项目化 |
| 一句话结论、单条、通用性未证 | `kb/ai-findings/findings.jsonl` | 有证据，但还只是单例 |
| 只有本次目标才成立 | 留在报告里 | 删掉目标名就失真 |

```bash
python scripts/misc/ai_finding.py add --kind path --area automation \
  --title "..." --trigger "..." --detail "..." --reuse high
python scripts/misc/ai_finding.py validate
```

**提案先于写入。** 跨技能或跨领域的改动交 `knowledge-architect` 走它的 CHECKPOINT；
本技能只负责把候选写成可检验命题并给出证据位置。

**反注水**：一次拆解没有产生新的通用技巧，就只留报告，不往知识层塞内容。

## 输出

报告骨架与日志呈现规范见 `references/teardown-report-template.md`。
落盘约定：机器可读产物进 `exports/third-party/`，人读报告进 `reports/third-party/`。

一份合格的拆解报告必须包含：**结论先行 → 结构清单 → 逻辑分层 → 复用分档（含 refuse）
→ 对照重写差异表 → 知识候选 → 未验证与未覆盖**。

## 与相邻技能的边界

- **`upstream-absorption`**：那条流程吸收的是**仓库的工程能力**（测量 / 记录 / 对照 / 回滚），
  对象是完整项目；本技能拆的是**一个脚本**，结论是"抄哪一段、怎么改"。
- **`knowledge-architect`**：它决定经验**该不该固化、写到哪**；本技能只出候选与证据。
- **`automation-script-dev-py` / `-js`**：P13 的 Pattern Mining 是**写脚本前读自己目录**
  建立基线；本技能读的是**别人的**代码，且结论要经过复用分档，不直接进入实施。
- **解密类技能**：目标脚本不可读时**先解密**再回来。在混淆代码上做复用判定，
  等于把"看不懂"当成"没有"。

## 反模式

- 把工具输出原样贴进报告，当成了结论。
- 报告里没有 `refuse` 一节——通常意味着没认真看风险，而不是目标脚本很干净。
- 复用候选里出现压缩 / 混淆文件的命中。
- 对照重写表只有"我会怎么做"，没有"为什么不同"和 Pattern 依据。
- 用"设计优雅""写得很规范"这类无法复核的词代替证据。
- 空目录 / 后缀不匹配时写"未发现可复用内容"，而不是"没有材料"。
- **把"缺口"一律读成"目标脚本没有这个能力"**。缺口至少有四个来源：**需求不同**
  （它本来就不需要这个能力）、**没有材料**（后缀不在范围、目录为空）、**读了看不进去**
  （加密载荷的关键词看不见）、**检测器没实现这门语言的写法**。只有第一条是"它没有"，
  后三条都是"我们这边没看见"——写报告时要说清是哪一种。
- 把目标脚本的真实域名、凭据、账号格式抄进报告或知识库。
- **拿"规则表 / 词表"类文件当目标**：关键词在那种文件里以字面量成片存在，
  会把几乎所有维度点亮。那是"文件里有这些词"，不是"脚本有这些能力"。
  实测把本套件自己的 `teardown_rules.py` 当目标扫，**25 个维度里有 20 个命中**
  （这个数会随规则表增长而变大——规则表越全，自指命中越多，正好说明它没意义）。
- **目标 Python 文件语法解析失败时直接采信能力矩阵**。`ast.parse` 一失败，
  符号表为空、文档字符串也没参与去散文过滤 → 能力矩阵**偏多**。
  工具会在提示里报出来（`⚠ N 个 Python 文件语法解析失败`），看到就得先查原因。
- **把风险标签写得比判据强**。`while True` 的标签曾经写"无界"、单次 `verify=False`
  的标签曾经写"全局关闭 TLS 校验"——**正则够不着 `break`，也分不清单次与全局**。
  报告是给人照着做的：一句过强的断言会让人去改一个本来就正常的东西。
  够不着就别断言，改成"正则能看见什么 + 你必须回去看什么"。

## 验证

改动或使用后至少跑：

```bash
python scripts/misc/script_teardown.py <目标> --json          # 工具可跑、报告可解析
python scripts/misc/run_offline_tests.py --strict              # 含本技能工具的离线用例
python scripts/misc/check_index.py                             # 新增脚本被文档点名
python scripts/misc/check_doc_refs.py                          # 报告里的路径可达
```
