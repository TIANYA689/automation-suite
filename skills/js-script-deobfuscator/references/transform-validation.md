# 改写语义验证

仅在反混淆、字符串解码、常量折叠、控制流简化或插桩时使用。**AST 能定位语法结构，不自动保证改写后行为等价。**

## 一、改写前后保留哪些证据

- 原脚本、候选脚本、各自 SHA-256 与 diff **分开保存**，避免覆盖唯一原样本。
- 先为目标签名/输出采集明确输入，包含时间、随机数、URL 原文与 Body 原文；环境依赖保持一致。
- **一次只改一条有解释的规则**，先用当前样本比较返回值、类型和异常，再用实际业务请求确认。
- 多个样本通过仅说明这些样本一致，**不是全程序等价证明**。
- 只有"可阅读"的解码视图要标为**分析副本**，不能直接替换生产签名逻辑。

## 二、必查的反例类型

| 改写 | 必须保留的语义 | 为什么 |
|---|---|---|
| 常量折叠 | 双精度浮点、负零、NaN/Infinity、字符串拼接与隐式类型转换 | 不能为好看截短小数；`-0` 与 `0` 在 `Object.is` 与除法中行为不同 |
| 按函数名替换调用 | 词法绑定 | 局部 `atob`/`parseInt` 等可能遮蔽全局同名函数，替换后指向错误的实现 |
| 自动解码 Base64/hex 字面量 | 编码字符串可能是实际业务输入 | 优先增加注释或另存候选视图，不直接替换其值 |
| 删除永假分支 | `var` 声明提升、块作用域与异常时机 | 删除分支可能连带删掉提升的声明，或改变抛错顺序 |
| 重写成员访问/函数调用 | `this`、getter/副作用次数、求值顺序、可选链与异常行为 | getter 可能计数或改变状态；求值顺序影响副作用 |
| 打印 trace | 区分原函数执行与序列化参数引发的副作用 | `JSON.stringify` 会触发 `toJSON`/getter，trace 本身改变了行为 |
| 展开 proxy object | 参数求值次数 | `helper.eq(a(), b())` 展开后若重复求值会多调一次 |

## 三、验证方法

1. **构造期望值**：从**原脚本的真实执行结果**构造非空期望值。
2. **禁止反向构造**：不要重新生成期望值来迎合候选输出——那等于没有验证。
3. **独立函数**：可在 Node 中直接比对新旧实现，输入需固定时间/随机源，或让函数显式接收这些值。
4. **绑定 DOM/SDK 的代码**：在需求项目的同一环境中分别运行新旧两版，比对结果。
5. **逐条回归**：每次只改一条规则，改完立即验证，不要攒一批再验。

## 四、判定标准

| 结果 | 结论 |
|---|---|
| 所有样本返回值、类型、异常均一致 | 该规则在已测样本上等价，可保留 |
| 任一样本不一致 | 该规则不等价，回退并记录反例 |
| 无法构造有效期望值 | 不判定通过，标记为"未验证" |
| 只在部分样本上一致 | 标记为"条件等价"，写清成立条件 |

**不允许**：把"没报错"当作"等价"；把"看起来合理"当作"正确"。

## 五、与控制流简化的配合

控制流平坦化还原后，必须验证：

- 状态转移顺序是否与原逻辑一致（含条件分支）。
- 循环边界与提前退出（`break`/`continue`/`return`）是否保持。
- 异常抛出位置是否保持。

建议做法：在还原前后各插入一次"状态序列日志"，比对序列是否一致。这比逐行读代码可靠。

## 六、与插桩的配合

插桩（源码级 tap）会改变源码，因此：

- 插桩产物必须与原脚本分开保存，并记录改写范围。
- 插桩可能触发完整性校验，一旦目标行为变化，先停插桩再判断。
- 插桩日志中的"对象预览"是占位，不是真实字段值；不要把占位当证据。

## 七、交付时的声明

交付报告里必须明确区分三类产物：

| 产物 | 性质 | 可否用于生产 |
|---|---|---|
| 原始脚本 | 权威副本 | 是（但不可读） |
| 验证通过的改写版 | 已证明在测试样本上等价 | 需用户确认后可用 |
| 分析副本（仅可读） | 未验证等价 | **否**，仅供阅读 |

把"分析副本"当"等价代码"使用是最常见的交付事故。
